개발은 Pleos 차량용 앱을 중심으로 진행하며 안드로이드 휴대폰은 연결된 차량의 보조 장치로 구성합니다. 차량 화면과 상태 처리는 Kotlin과 Compose를 사용하고, 서버는 TypeScript 기반 API와 PostgreSQL, 파일 저장소로 나눕니다. 차량 정보 수신, 판정, 화면 갱신, 파일 보관, 통지는 기다리느라 멈추지 않도록 분리합니다. 현재 작성한 상세 기획과 API 및 데이터 계약을 개발 기준으로 삼되, 실제 SDK 권한과 대상 장치 동작을 확인한 뒤 기능을 활성화합니다.

첫 단계에서는 사용할 수 있는 차량 정보를 확인합니다. Vehicle SDK의 브레이크와 에어백, 차량 기본 상태와 경고 관련 기능을 확인하고, 속도는 허용된 공식 차량 속성 경로를 검증합니다. 위치와 음성 인식, 음성 출력, 내비게이션 연결도 목적에 맞게 연동합니다. 원시 CAN이나 차량 하드웨어 계층에 직접 접근하는 방법을 전제로 하지 않습니다. 권한이 없거나 대상 차량에서 제공하지 않는 정보는 미지원으로 표시하고 수동 입력 경로를 먼저 연결합니다.

수신 자료에는 값과 단위뿐 아니라 출처, 실제 측정 시각, 받은 시각, 품질 상태를 함께 저장합니다. 브레이크 값이 없을 때는 눌리지 않았다고 바꾸지 않고 확인 불가로 처리합니다. 마지막 측정 후 3초 이상 지난 값은 오래된 자료로 분리하며, 같은 값을 다시 받았다는 이유만으로 물리 센서가 새로 측정됐다고 가정하지 않습니다. 서로 다른 기기 시계를 비교할 때는 기준과 오차를 관리합니다. 화면에는 현재 판단에 쓴 자료가 유효한지 함께 표시합니다.

진동 분석은 차량에 고정된 가속도계와 자이로스코프가 제공되는지 확인한 뒤 개발합니다. 휠 정보, 조향각, 엔진이나 모터 회전수도 공개 범위와 권한을 따로 검증합니다. 장착 방향과 단위, 수집 속도를 맞추고 순간 충격과 지속 진동을 나누어 분석합니다. 주파수와 진폭 기준은 개발용 실험값으로 관리하며 검증 전 자동 판정은 기본적으로 끕니다. 빠진 샘플을 복제해 정상 측정처럼 보이게 하지 않고, 분석에 필요한 주기가 부족하면 수동 기록으로 전환합니다.

경고등 도감은 차량과 사양, 소프트웨어 범위에 맞는 공식 자료를 항목별로 검토해 구축합니다. 필요한 전체 항목 수와 가져온 수, 검토를 마친 수를 구분해 관리하고 검토되지 않은 설명은 완료 항목으로 표시하지 않습니다. 사진 검색은 후보를 추출한 뒤 사용자가 확인하도록 구현합니다. 대처 문구와 긴급 그림은 차량의 장치 배치 및 공식 절차와 대조합니다. 안내 자료는 버전을 남겨 어떤 설명을 제공했는지 사건 기록에서 다시 확인할 수 있게 합니다.

기록 기능은 최근 구간을 임시로 보관하다 사건이 생기면 필요한 구간을 고정하는 구조로 구현합니다. 초기 시험은 발생 전 30초와 이후 60초를 기준으로 삼습니다. 원본 녹음과 영상, 외부 마이크와 블랙박스는 실제 연동 가능 여부를 확인한 채널만 추가합니다. 저장 공간이 부족해도 작은 사건 정보와 누락 사유는 남기도록 합니다. 파일 전송은 나눠 보내고 중단된 위치에서 다시 이어 보냅니다. 수신 길이와 해시를 확인하기 전에는 원본 보관이 완료됐다고 표시하지 않습니다.

차량 화면은 가로형 앱 영역을 기준으로 설계하며 전체 화면과 분할 창의 실제 크기에 맞춰 조정합니다. 차량 그림의 부위 선택과 아이콘을 중심에 두고, 경고 도감과 파형 기록, 긴급 안내, 보호자 지도는 서로 다른 화면 구성을 사용합니다. Pretendard의 굵기와 색 대비, 터치 간격을 실제 환경에서 확인합니다. 시스템의 주행 화면과 보호 영역을 가리지 않으며 주행 중 제한을 우회하지 않습니다. 음성과 설명 그림은 같은 상태를 참조해 서로 다른 행동을 안내하지 않도록 합니다.

서버는 사건과 기록 자료, 위치, 보호자 권한, 통지 작업을 분리해 관리합니다. 상세 별첨의 23개 API 작업과 23개 데이터 테이블을 출발점으로 요청과 응답, 오류, 재시도, 삭제 규칙을 구현합니다. 카카오톡 발송은 승인된 일반 알림 템플릿과 계약을 사용하고 문자 대체는 서버가 맡습니다. 첫 발송 요청 시점부터 기한을 계산해 응답이 끊긴 경우도 처리합니다. 접수와 전달, 열람을 구분하고 같은 사건의 중복 발송 및 발송 직전 취소가 충돌하는 경우를 시험합니다.

휴대폰 백업은 사고가 난 뒤 처음 준비하는 기능이 아니라 출발 전에 연결과 권한을 확인하는 기능으로 만듭니다. 차량에서 마지막으로 받은 사건, 안내 단계, 위치와 시각을 보관하고 전원 중단 시 가능한 안내와 전송을 이어갑니다. 휴대폰 자체 센서는 별도 출처로 기록하며 차량의 새 센서값으로 취급하지 않습니다. 두 기기가 동시에 복구됐을 때 같은 사건을 합치고 이미 수행한 통지를 반복하지 않도록 합니다. 운영체제의 백그라운드 제한과 연결 해제를 실제 기기에서 확인합니다.

개인정보 처리는 개발 초기부터 함께 구현합니다. 차량과 보호자의 접근 권한을 서버에서 확인하고, 자료의 보관과 공유, 삭제를 사건 단위로 관리합니다. 발송사 비밀키는 차량이나 휴대폰에 넣지 않습니다. 전송 실패 때 재시도할 자료와 이미 완료된 작업을 구분하고, 권한이 철회되면 새로운 공유와 발송을 막는지 확인합니다.

개발 순서는 기능 확인, 도감과 화면, 기록과 판정, 서버와 통지, 휴대폰 백업 검증으로 나눕니다. 각 단계는 화면을 만들었다는 점만으로 완료하지 않고 입력과 오류 처리 결과를 확인합니다. 확인이 끝나지 않은 연결은 시험 표시를 유지하며, 개인 참가자가 개발과 검토해야 할 작업을 단계별로 관리합니다. 결과를 남겨 둡니다.

검증은 문서에 정의한 인수 시나리오 56개를 실제 구현과 연결하는 방식으로 진행합니다. 정상 입력뿐 아니라 결측, 오래된 값, 시간 오류, 저장 부족, 통신 단절, 앱 재시작과 전원 중단을 포함합니다. 공모전 시연에서는 실제 SDK 수신값과 시험용 입력을 명확히 나누어 보여 줍니다. 현재 완료한 것은 기획, 계약 파일, 화면 설계와 일부 정적·합성 검사이며 실차 센서, 알림톡 발송, 사고 대응 성능은 아직 시험하지 않았습니다. 검증된 기능부터 공개하고 확인되지 않은 기능은 예정 또는 미지원으로 표시하겠습니다.
