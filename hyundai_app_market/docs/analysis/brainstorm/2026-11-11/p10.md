## 아이디어 3개

- **이름: 문턱 앞 한 가방.** 다음 방문에 필요한 물건을 차에서 한 번 듣고 한 가방에 챙기는 출발 전 준비표.
- **사용 장면:** 기사 자신이 미리 적은 방문 메모와 공구·부품 목록을 주차 후 불러온다. 차 밖에서는 실제 물건을 꺼내 가방에 담고 고객 집으로 가져간다. 작업장 문턱에서 메모를 다시 여는 단계를 덜자는 가설이다.
- **차에서 할 이유:** 공구와 부품을 싣고 있는 차가 준비 장소이자 다음 작업의 시작점이다. 다음 집의 물건만 차량 오디오로 읽으면 적재함을 살피면서 목록을 들을 수 있다는 유추다. 적재함 밖에서의 청취 가능성은 별도 검증한다.
- **SDK·외부 데이터 가정:** [TTS](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/TextToSpeech/intro)의 ON_DEVICE 합성을 후보로 삼는다. 방문 순서·준비물은 기사 수동 입력과 앱 내부 저장이다. 공구 RFID, 부품 자동 인식, 카메라, 고객 예약 API, 휴대폰 연동을 전제하지 않는다.
- **작은 시연 흐름:** 가상 방문 A·B와 각 준비물 2개를 사전 입력 → 주차 중 A 선택 → 목록 읽기 → 실제 소품을 차 밖 가방에 담기 → 차에서 준비 완료 선택 → B 목록 전환. 물건을 챙겼다는 판단은 사람이 한다.
- **약점·검증 질문:** 목록을 만드는 일이 또 다른 일이 될 수 있다. 실제 기사에게 기존 메모보다 준비물 입력·수정의 부담이 작은지 묻는다.
- **실제 문제 근거:** [S1](#s1)은 수리점에서 먼 마을 방문과 현장 수리를, [S2](#s2)는 여러 소형 농기계의 현장 정비를 설명한다. 방문별 준비를 다룰 맥락은 있지만 공구 누락 빈도나 가방 방식의 효과를 입증하지 않는다.

---

- **이름: 부품 한 줄, 귀가 한 코스.** 쓴 부품을 별도 장보기 메모로 다시 옮기지 않고 귀가 경유지와 함께 남긴다.
- **사용 장면:** 수리를 마치고 차에 돌아온 기사가 주차 상태에서 부족한 부품과 수량을 말하거나 입력한다. 마지막 방문 뒤 미리 등록한 부품점 한 곳을 직접 선택하고 보충 목록을 확인한다.
- **차에서 할 이유:** 보충할 물건을 기억하는 시점과 다음 이동을 정하는 시점이 만난다. 작업 기록과 내비 목적지를 번갈아 열며 옮기는 단계를 덜자는 제안이다.
- **SDK·외부 데이터 가정:** [STT](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/SpeechToText/intro)로 받은 최종 텍스트를 기사 확인 후 저장하고, [NaviHelper 경유지 요청](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/route-with-waypoints)으로 사용자가 선택한 점포 1곳과 귀가 목적지를 전달한다. 점포 좌표·품목명은 수동 등록이며 재고·가격·영업시간·최적 순회 순서를 알지 못한다.
- **작은 시연 흐름:** 주차 중 “부품 A 두 개 보충” 입력 → 인식 텍스트 수정·확인 → 사전 등록 점포 선택 → 보충 목록과 요청 경로 표시 → 내비 완료 또는 오류 이벤트 표시. 음성이 실패하면 터치 입력으로 같은 흐름을 보인다.
- **약점·검증 질문:** 잘못 인식한 부품 규격은 구매 오류로 이어질 수 있다. 기사에게 평소 쓰는 품번을 직접 입력하는 편과 음성 확인 중 어느 쪽이 덜 번거로운지 묻는다.
- **실제 문제 근거:** [S2](#s2)는 순회수리에서 부품 지원을 제공한다고 적는다. 부품이 현장 서비스의 구성 요소라는 좁은 근거다. 민간 기사에게 재고 부족·반복 구매가 얼마나 발생하는지와 이 흐름의 절감 효과는 미확인이다.

- **이름: 스패너의 귀가 사연.** 공구가 라디오에 사연을 보낸다는 설정으로 작업 종료 확인표를 읽는 엉뚱한 도구 회수 방송.
- **사용 장면:** 작업 후 주차된 차에서 “저는 렌치 A입니다. 오늘 가방으로 돌아왔을까요?”라는 짧은 문장을 듣고 본인이 확인한다. 밖에 남은 물건은 다시 내려가 직접 가져온다. 실제 라디오 사연 수집·송출 기능은 없다.
- **차에서 할 이유:** 현장을 떠나기 전 차로 돌아온 순간에 회수 여부를 돌아보게 한다. 좋아하는 사연 방송 형식을 빌려 딱딱한 확인표를 듣고 싶은 것으로 만들 수 있다는 취향 기반 가설이다.
- **SDK·외부 데이터 가정:** [TTS](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/TextToSpeech/intro) ON_DEVICE와 앱에 직접 작성한 문장 틀을 사용한다. 공구 별명·회수 상태는 수동 입력한다. 생성형 AI, 방송사 콘텐츠·실존 진행자 목소리, 자동 분실 감지, 트렁크 센서나 잠금 제어를 요구하지 않는다.
- **작은 시연 흐름:** 가상 공구 3개를 등록 → 주차 중 회수 방송 시작 → 2개는 확인, 1개는 미확인 표시 → 현장으로 걸어가 소품 회수 → 차에서 마지막 항목 확인 → “오늘의 출연진 전원 귀가”로 종료. 미확인은 실제 분실 판정이 아니다.
- **약점·검증 질문:** 농담이 반복되면 확인 동작만 늘어날 수 있다. 기사에게 사연형·이름만 읽기·무음 목록 중 계속 쓸 방식을 묻는다.
- **실제 문제 근거:** [S1](#s1)의 방문 수리 운영은 떠나기 전 마무리 확인을 놓아 볼 맥락이다. 공구를 자주 잃는다는 연구 근거는 확보하지 않았다. 재미 요소와 회수 확인에 대한 수요는 페르소나에서 발상한 가설이다.

## 구현 가정·우선 확인·검증 한계

- 제안 구조는 차량 앱의 수동 입력·내부 목록 저장 → TTS 안내 또는 STT 텍스트 확인 → 필요할 때 내비 경유지 요청이다. STT가 업무를 자동 실행하지 않으며 텍스트 저장·확인과 경로 요청은 앱이 별도로 구현해야 한다. 앱 코드와 시연물은 작성하지 않았다.
- 공모전 허용 범위는 [공식 개발 범위 공지](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000008) 및 같은 날 SDK 리뷰 기준이다. Vehicle·NaviHelper·TTS·STT·FusedLocation 다섯 SDK 모두 사용 가능하다. 세 발상은 TTS·STT·NaviHelper만 후보로 쓰며, Gleo 승인·Pleos LLM SDK·차량 마이크의 외부 STT 업체 전송을 설계에 넣지 않았다.
- ON_DEVICE는 서버 앱 등록을 요구하지 않는 문서상 모드지만 실제 에뮬레이터의 한국어 엔진 지원·마이크·오디오 출력은 확인하지 않았다. 자체 서버나 외부 재고 API를 확보했다고 가정하지 않는다. 내비 연결·권한·좌표·요청 결과도 미실행이다.
- 먼저 확인할 것은 실제 기사의 기존 준비·보충·회수 절차와 수동 입력 부담이다. 제품 질문은 방문 전과 후 중 어느 시점에 확인표를 두어야 덜 번거로운가이다. 효과·안전성·유료 수요는 검증하지 않았다.
- 실행한 확인: 로컬 지침·기존 SDK 문서 읽기, 파일 이름 검색, Git 저장소 여부 확인, 공개 원문 열람. 두 현장 자료를 `agbrowse fetch <URL> --json --browser never`로 읽었고 둘 다 HTTP 200·`strong_ok`·본문 비절단이었다. 응답에 전체 조사 `evidenceStatus`는 없어 자동 `sufficient` 판정으로 표시하지 않는다. S2는 웹 도구 열기가 실패한 뒤 CLI로 본문을 확인했다. SDK 원문은 TTS 소개·STT 소개·경유지 요청 페이지를 열었다.
- 실시하지 않은 것: 인터뷰, 농촌 현장 관찰, APK 빌드, 에뮬레이터·실차 실행, 음성 인증, 실물 공구·부품 인식, 내비 경로 실행, 실제 작업 시간 비교. 위 시연은 앞으로 보여 줄 수 있는 제안 순서다.

후속 인계: 기존 공모전·SDK 보고서를 먼저 읽고, 이 파일의 가상 설정·근거 범위·미실행 구분을 유지하며 새 검증 결과만 갱신한다. 통합 요약과 프로젝트 지침 갱신은 부모 작업 범위이며 이 작업은 P10 파일만 작성했다.
