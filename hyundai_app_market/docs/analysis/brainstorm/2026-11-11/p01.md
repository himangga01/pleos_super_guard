## 1. 해뜨기 전 12분

- **한 줄 제안:** 차량 도착 시각에 주차 후 걷기·장비 설치 시간을 더해, 원하는 빛을 맞을 준비가 되는 시각을 보여준다.
- **구체 장면:** 가상의 일출 06:40, 사용자가 고른 준비 완료 목표 06:28, 주차장 도착 06:12, 도보 8분·설치 5분이면 여유는 3분이다. 도착 예상이 06:18로 바뀌면 준비 완료가 06:31이 되어 목표보다 3분 늦음을 표시한다. 12분은 사용자가 정한 값이며 촬영의 보편적 정답이 아니다.
- **차에서 해야 할 이유:** 내장 내비의 남은 이동 시간과 촬영 준비의 마감 시각을 같은 화면에서 계산한다. 주차장 도착과 촬영 준비 완료를 구분하므로 이동 마지막 구간의 반복 계산을 줄일 수 있다는 가설이다. 목표 변경은 정차 후 선택한다.
- **불편의 근거와 해석:** 미국 국립공원관리청은 구름 때문에 먼 길을 운전하고도 별을 못 볼 수 있어 출발 전 날씨 확인을 권한다[E1]. 미국 해군천문대는 날짜·위치별 일출과 시민박명 시각을 제공한다[E3]. 이를 촬영 준비 시각 계산에 결합하는 수요는 아직 확인하지 않았다.
- **핵심 SDK:** NaviHelper 3.0.5의 목적지 설정·정보 조회와 `remainTime`을 우선 검토한다[D1·D2]. FusedLocation 1.1.3으로 차량 위치를 받아 목적지·시간대 입력을 보조한다[D3]. 실제 이벤트 수신과 시간 단위는 시연 구현 전에 확인해야 한다.
- **외부 데이터·차 밖 경험 가정:** 일출은 USNO 또는 국내 천문 자료, 날씨는 기상청 서비스[E4]를 연결한다고 가정한다. 사용자가 등록한 주차 지점·도보·설치 시간과 체크리스트를 QR로 휴대폰 웹 화면에 넘겨 하차 후 이어본다. 휴대폰 연계·서버·도보 안내는 별도 구현 가정이다. 산 능선·현장 구름·촬영 가능성을 계산했다고 주장하지 않는다.
- **첫 시연 흐름:** Pleos 화면에서 촬영지 선택 → 고정 일출·날씨 자료에 ‘시연 데이터’ 표시 → 내비 목적지 요청과 성공·실패 표시 → 남은 시간 변화에 따른 준비 여유 재계산 → 하차용 카드 미리보기. 실제 SDK 이벤트와 주입한 값은 화면에서 구분한다.
- **약점·검증 질문:** 현장 도보·설치 시간 오차가 내비 오차보다 클 수 있다. “촬영자는 한 번 입력한 준비 시간을 다음 방문에도 다시 쓸 만큼 장소별 습관이 일정한가?”를 먼저 확인한다.

## 2. 배터리 교대조

- **한 줄 제안:** 촬영하러 내리고 장비를 싣는 순간에, 예비 배터리와 온도 경계를 넘는 장비의 준비를 짧게 챙긴다.
- **구체 장면:** 겨울 새벽 촬영 전 차량 화면에서 배터리 A는 카메라, B는 예비 파우치로 체크한다. 촬영 후 ‘장비 복귀’를 누르면 배터리 상태의 수동 기록과 카메라를 밀폐 가방에 넣는 확인 항목을 보여준다. 잔량·장비 온도를 자동 측정했다고 표시하지 않는다.
- **차에서 해야 할 이유:** 차량은 따뜻한 실내와 야외 사이에서 장비를 반복해서 싣고 내리는 경계다. 큰 체크 항목과 짧은 음성 안내로 가방을 들고 휴대폰 목록을 다시 찾는 일을 줄일 수 있다는 가설이다.
- **불편의 근거와 해석:** Nikon Z6III 공식 설명서는 저온에서 배터리 용량이 줄며, 추운 날 충전된 예비 배터리를 따뜻한 곳에 준비하도록 안내한다. 급격한 온도 변화 전 밀폐 가방·케이스를 사용하고 적응 시간을 두도록도 설명한다[E2]. 모든 카메라에 같은 온도·대기 시간을 적용한다는 뜻은 아니다.
- **핵심 SDK:** Vehicle 2.3.2의 문 상태 읽기·이벤트를 Capability와 해당 영역 권한 확인 후 보조 신호로 쓴다[D4]. 문이 열린 사실은 장비 이동의 증거가 아니므로 사용자가 시작한 촬영 세션에서만 확인 카드를 제안한다. TTS 3.3.1의 ON_DEVICE 안내를 검토한다[D5].
- **외부 데이터·차 밖 경험 가정:** 장비 모델·배터리 준비 여부·사용 상태는 수동 입력하고 제조사 설명서 링크를 붙인다. 기상청 기온 정보 연계는 가정이다[E4]. 휴대폰의 ‘촬영 중 사용한 배터리’ 체크를 차량에 되돌리는 동기화도 별도 가정이다. 차량 전원·카메라 충전기 제어와 장비 온도 추론은 포함하지 않는다.
- **첫 시연 흐름:** Pleos에서 ‘촬영 출발’ 선택 → 지원되는 문 상태 또는 명시된 시연 이벤트 수신 → 배터리 2개 체크·짧은 음성 → ‘장비 복귀’ 선택 → 제조사 지침을 연결한 가방 확인 → 사용 기록 저장. 문 이벤트 미지원 시 사용자 버튼으로 이어간다.
- **약점·검증 질문:** 체크 자체가 피로를 더할 수 있다. “배터리 이름 두 개와 사용 상태만 기록하는 정도라면 촬영자가 다음 출사에도 계속 입력하는가?”를 확인한다. 결로 방지·장비 보호 성공을 보증하거나 임의의 안전 대기 시간을 제시하지 않는다.

## 3. 별빛 입국심사

- **한 줄 제안:** 관측지에 도착한 차량을 우주 입국심사대로 삼아, 밝은 화면을 정리하고 어둠에 적응할 시간을 장난스럽게 준비한다.
- **구체 장면:** 정차 확인 후 캐릭터가 ‘백색광 소지품을 신고하세요’라고 말한다. 사용자는 손전등·휴대폰·차량 조명을 확인하고 관측 준비를 마친다. 화면에는 ‘눈이 우주에 적응하는 중’ 도장을 찍고 사용자가 고른 준비 시간을 표시한다. 눈의 실제 상태를 측정하지 않는다.
- **차에서 해야 할 이유:** 내비를 끝내고 조명·가방·휴대폰을 정리하는 도착 순간을 한 번에 묶는다. 차량 화면과 음성으로 관측 준비를 끝내고, 하차 후 별을 보면서 휴대폰 안내를 계속 읽는 일을 줄일 수 있다는 가설이다.
- **불편의 근거와 해석:** NPS는 손전등·휴대폰·차량 전조등의 백색광과 밤 시야의 관계를 설명하며, 매우 어두운 환경에 눈이 적응하는 데 20~30분이 걸린다고 안내한다[E1]. 이 일반 안내를 재미있는 준비 의식으로 바꾸면 반복 사용한다는 부분은 서비스 가설이다.
- **핵심 SDK:** FusedLocation 1.1.3으로 선택한 관측지 근처 도착을 제안하고 사용자가 정차·도착을 확인한다[D3]. TTS 3.3.1 ON_DEVICE로 짧은 심사 대사를 재생한다[D5]. 대사는 미리 작성한 규칙 기반 문장으로 충분하며 LLM·외부 STT가 필요하지 않다.
- **외부 데이터·화면 가정:** NPS 안내를 출처와 함께 재서술하고, 선택적으로 달 뜨고 지는 시각을 USNO에서 가져온다고 가정한다[E3]. 앱 내부는 검은 배경과 최소한의 붉은 글자를 검토한다. 패널 밝기·시스템 알림·다른 화면까지 제어된다는 가정은 두지 않는다. 차량 조명은 정차 상태에서 사용자가 확인한다.
- **첫 시연 흐름:** Pleos에 관측지 도착 카드 → 사용자 정차 확인 → ‘백색광 신고’ 항목 3개 → 짧은 TTS 대사 → 준비 시간 시작 → 시연용 시간 이동으로 입장 도장 표시. 20초로 압축한다면 ‘시연에서만 시간 압축’이라고 표시한다. 하차 후 경험은 휴대폰을 넣고 실제 하늘을 보는 행위로 이어진다.
- **약점·검증 질문:** 차 안의 다른 광원과 하차 후 환경을 앱이 통제하지 못한다. “사용자는 이 입국심사를 첫날의 농담으로 끝내지 않고 다음 관측에서도 준비 습관으로 쓰는가?”를 확인한다. 정차 중의 취미 준비 기능이며 의료 효과나 운전 안전을 보증하지 않는다.

## 실제 확인과 미실행 검증

- 실행한 작업: 지침·기존 보고서·SDK 노트 읽기, 로컬 목록·Git 여부 확인, 외부 원문 열람, Markdown 작성. E1~E4의 `agbrowse search --verify URL --json --browser never` 결과는 모두 `strong_ok`, `source: fetch`, `chromeUsed: false`였다. 이 단일 URL 형식은 `evidenceStatus`를 반환하지 않으므로 종합 자동 검증 완료로 해석하지 않는다.
- 실패한 경로: Nikon 지원 사이트의 별도 문서는 웹 시간 초과와 CLI `blocked`가 발생했다. 성공적으로 연 공식 Z6III 설명서 E2로 근거를 한정했다.
- 미실행: Android·SDK 설치, 코드 작성, 빌드, 에뮬레이터·실차·권한·음성·문 이벤트·내비 시간·위치 호출, 외부 API 인증·호출, 휴대폰 연계, 현장 촬영, 사용자 인터뷰·재이용·사업성 검증. 위 ‘첫 시연 흐름’은 앞으로 만들 수 있는 작은 흐름이며 실행 기록이 아니다.
- 우선 확인할 가설: P01-1의 도보·설치 시간 기록이 반복 방문에서 재사용되는지, P01-2의 수동 체크가 부담인지, P01-3의 의식이 반복 사용으로 이어지는지다. 순위·수익성·시장 최초를 입증한 결과는 없다.
- 후속 작업은 이 파일과 정식 SDK 리뷰를 먼저 읽고, 이 페르소나의 새 근거·검증 결과가 생긴 경우 이 파일을 갱신한다. 공통 보고서와 AGENTS.md의 인계 갱신은 상위 종합 작업에서 처리한다.
