# 차량 안전 앱 세 가지 구체화

작성일: **2026-11-12, 한국 시간**.

**후속 변경:** 사용자의 지시에 따라 경고등 도감·이상 가속 대응·사고 공유를 [Pleos 중심 통합 앱](integrated-vehicle-care-2026-11-12.md)으로 합쳤습니다. 브레이크 입력 후 감속 실패 안내, 음성·화면 애니메이션, 순간 고장 기록, 블랙박스, 구조 요청 음성, 안드로이드 백업을 포함한 현재 계획은 해당 문서를 따릅니다. 아래는 통합 전 기획과 정적 조사 이력입니다.

전체 비교는 [여섯 아이디어 요약](six-app-ideas-2026-11-12.md)에 정리했습니다. 요약에서는 이상 가속 알림과 페달 확인을 한 안으로 묶었으며, 이 문서의 세 가지 상세 기획은 유지합니다.

이 문서는 이상 가속 대응, 페달 착각 예방, 사고 전후 기록과 보호자 공유를 구체화한 기획안이다. 내부·외부 마이크, 놀란 말의 인식, 차량 속도와 기울기를 함께 검토했다. 앱과 서버를 만들거나 실제 차량에서 시험한 결과는 아니다.

**내부 마이크의 말을 글로 받는 기능과 차량 속도를 읽는 공식 경로는 확인했다. 외부 마이크, 원본 녹음, 차량 카메라, 차량 기울기는 실제 장치와 사용 권한을 확인해야 한다. 공개 SDK에서 차량을 강제로 멈추는 기능은 확인되지 않았다.**

| 제안 | 하는 일 | 현재 확인한 개발 범위 |
| --- | --- | --- |
| 1. 이상 가속 알림 | 속도·브레이크 상태·놀란 말을 함께 살펴보고 관련 기록을 보관한다. | 읽을 수 있는 신호를 이용한 알림과 기록. 자동 제동은 제조사 협력이 필요하다. |
| 2. 페달 확인 도우미 | 출발 전 브레이크 입력을 확인하고, 별도 연습 장치에서 페달 착각을 줄이는 연습을 한다. | 브레이크 입력 확인. 가속 페달의 눌린 정도는 추가 확인이 필요하다. |
| 3. 사고 기록과 보호자 알림 | 위험이 의심되거나 사고 신호가 들어오면 사고 전후의 기록을 보관하고 보호자에게 전달한다. | 사용을 허용받은 차량 정보·위치·인식한 말부터 구성한다. 영상·원본 소리는 조건부로 추가한다. |

앱 이름은 기능을 설명하기 위해 정한 임시 이름이다. 세 가지를 별도 앱으로 만들 수도 있고, 사고 기록 앱 안에 두 보조 기능을 넣을 수도 있다.

## 1. 마이크와 센서에서 확인한 내용

SDK는 앱이 차량 기능을 사용할 때 쓰는 개발 도구다. 아래의 ‘확인’은 공식 문서나 배포 파일에 기능이 있다는 뜻이다. 특정 차량에서 사용이 허용되고 값이 들어온다는 뜻까지 포함하지 않는다.

| 필요한 정보 | 조사 결과 | 앱에 넣을 방법 |
| --- | --- | --- |
| 내부 마이크의 말 | SpeechToText가 차량 마이크로 받은 말을 글로 전달한다. | 놀란 표현과 그 말을 인식한 시각을 기록한다. |
| 내부 마이크의 원본 소리 | 음성 인식 결과에서 원본 녹음 파일을 받는 기능은 확인하지 못했다. | 별도로 허용된 녹음 경로가 확인되면 추가한다. |
| 외부 마이크 | 공개 문서와 확인한 인터페이스에서 외부 마이크 선택·녹음 경로는 확인되지 않았다. | 지원 장치와 공식 접근 방법이 확인될 때 추가한다. |
| 실제 차량 속도 | Pleos 공식 FAQ가 차량 운영체제의 속도 조회 방법을 안내한다. | 차량 신호에서 받은 속도를 기록한다. GPS 속도와 출처를 구분한다. |
| 브레이크를 밟았는지 | Vehicle SDK에 조회와 변경 알림 기능이 있다. | ‘밟음’, ‘밟지 않음’, ‘확인 불가’로 구분한다. |
| 가속 페달을 얼마나 밟았는지 | Android 차량 API에는 해당 항목이 있다. Pleos 대상 차량의 제공 여부는 미확인이다. | 사용할 버전·차량·권한을 확인한 뒤 추가한다. |
| 브레이크를 얼마나 밟았는지 | Android 차량 API에는 페달이 눌린 비율이 있다. 대상 차량의 제공 여부는 미확인이다. | 비율을 받을 수 있을 때 추가한다. 누른 힘이나 제동력으로 표시하지 않는다. |
| 차량 기울기 | 확인한 Pleos Vehicle API에서 차체 기울기 조회 기능은 찾지 못했다. | 사용 가능한 기울기·회전 센서 또는 제조사 제공 신호가 있는지 확인한다. |
| 가속도와 회전 속도 | Android는 관련 센서를 지원하지만 Pleos 장치에서 제공될지는 미확인이다. | 센서가 있고 사용이 허용되면 장착 방향을 맞춰 기록한다. |
| 핸들 각도 | Vehicle SDK에 조회와 변경 알림 기능이 있다. | 핸들이 돌아간 정도를 기록한다. 차체가 기운 정도와 구분한다. |
| 에어백이 펼쳐졌는지 | Vehicle SDK에 좌석 영역별 조회와 변경 알림 기능이 있다. | 새로 펼쳐졌다는 신호를 받으면 긴급 기록을 시작한다. |
| 위치 | FusedLocation SDK에 위치 조회 기능이 있다. | 좌표·정확도·위치를 얻은 시각을 함께 보관한다. |
| 차량 안팎 영상 | 확인한 Vehicle API에는 일반 앱용 영상 녹화 기능이 없다. 차량 카메라의 접근 권한도 미확인이다. | 사용을 허용받은 카메라나 블랙박스의 공식 연결 기능이 있을 때 추가한다. |
| 그 밖의 차량 상태 | SDK에 안전벨트·문·타이어·배터리·연료 등 여러 항목이 있다. | 해당 차량에서 지원하고 읽기 권한이 있는 항목만 선택한다. |

음성 인식은 [시작·종료 안내](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/SpeechToText/start-and-stop)와 [결과 안내](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/SpeechToText/result-listeners), 속도는 [Pleos 공식 FAQ](https://document.pleos.ai/en/docs/pleos-only/vehicle-app-developer-guide/vehicle-app-faq), 페달 항목은 [Android 차량 정보](https://developer.android.com/reference/android/car/VehiclePropertyIds)를 확인했다. 센서와 하드웨어의 실제 사용 조건은 [Android 센서 안내](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview)와 [Pleos 플랫폼 안내](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/platform-api-architecture)를 따른다.

함수 이름과 권한, 배포 파일 확인 결과는 [SDK 기능 조사](../sdk/vehicle-safety-capabilities.md)에 따로 정리했다.

## 2. 내부 마이크로 놀란 말을 알아듣는 방법

### 2.1 무엇을 알아들을 것인가

사용자가 제시한 표현을 첫 시험 문장으로 삼는다.

| 인식한 말 | 앱에서 읽을 수 있는 뜻 | 이 말만으로 알 수 없는 것 |
| --- | --- | --- |
| ‘어 이거 왜이래!’ | 예상과 다른 일이 생겼다고 말했을 가능성이 있다. | 차의 문제인지, 휴대폰이나 다른 일의 문제인지 알 수 없다. |
| ‘아이고!’ | 놀라거나 불편함을 나타냈을 가능성이 있다. | 사고인지, 단순한 대화인지 알 수 없다. |
| ‘안돼!’ | 어떤 일을 막고 싶다는 뜻일 수 있다. | 차를 멈추려는 말인지, 동승자나 방송의 말인지 알 수 없다. |

앱은 먼저 말을 글로 받은 뒤 띄어쓰기와 문장부호 차이를 정리한다. ‘왜이래’와 ‘왜 이래’처럼 같은 표현을 함께 찾는다. 같은 인식 과정에서 문장이 여러 번 바뀌면 한 번의 말로 묶는다.

그다음 해당 시각의 속도, 브레이크 입력, 가능한 경우 가속 페달 입력과 움직임을 함께 살핀다. **인식한 말은 위험을 의심하는 자료로 사용한다. 사고 원인이나 운전자의 실수를 확정하는 자료로 사용하지 않는다.**

음성 인식 SDK가 사람의 의도나 감정을 자동으로 알려 주는 것은 아니다. 말의 뜻을 분류하는 규칙은 앱에서 만들어야 한다. 운전자·동승자·라디오의 목소리를 정확히 구분하는 기능도 확인되지 않았다.

### 2.2 어떤 행동으로 이어질 것인가

아래는 제안한 동작이다. 효과를 검증한 사고 판정 규칙은 아니다.

| 들어온 자료 | 제안한 동작 | 화면과 보호자에게 표시할 표현 |
| --- | --- | --- |
| 놀란 말만 인식 | 최근 기록에 표시하고, 허용된 범위에서 덮어쓰기를 멈춘다. | ‘확인이 필요한 말 인식’ |
| 놀란 말과 유효한 차량 이상 변화가 함께 관측됨 | 관련 기록을 보관하고, 사전 동의한 조건에 따라 보호자에게 알림을 보낸다. | ‘위험 상황 의심’. 받은 자료와 빠진 자료를 함께 표시 |
| 새 에어백 전개 신호 또는 사용자의 긴급 요청 | 음성 결과를 기다리지 않고 우선 알림과 기록 보관을 진행한다. | ‘에어백 전개 신호 수신’ 또는 ‘사용자 긴급 요청’ |
| 음성 인식이 꺼졌거나 실패함 | 차량 신호와 수동 요청만 사용한다. | ‘음성 인식 중지’ 또는 ‘음성 인식 오류’ |

중간 인식 결과로 기록 보관을 먼저 준비할 수 있다. 최종 문장을 기다리느라 다른 사고 신호의 처리를 늦추지 않는다. 인식 결과가 도착한 시각과 실제 말을 한 시각은 다를 수 있으므로 구분해서 보관한다.

### 2.3 녹음과 외부 마이크

글로 인식한 문장과 원본 녹음은 다른 자료다. 현재 확인한 결과 전달 기능에는 원본 소리를 앱에 내보내는 항목이 없다. 소리 크기를 나타내는 값도 사고 충격의 크기나 정확한 소음 측정값으로 쓸 수 없다.

외부 마이크를 사용할 수 있다면 충격음·경적 등 주변 소리를 별도 자료로 보관하는 안을 검토한다. 소리만으로 충돌을 확정하지 않는다. 바람·공사·문 닫는 소리를 구분하는 시험도 필요하다. 이 기능은 SDK에 이미 있는 충돌음 감지 기능으로 설명하지 않는다.

차량 마이크의 소리를 외부 음성 인식 업체로 보내는 방법은 공모전에서 허용되지 않는다. 먼저 제공된 SpeechToText를 사용한다. 음성 인식 허용이 원본 녹음·보호자 전송 허용까지 뜻하는 것은 아니다. [공모전 개발 범위](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000008)

## 3. 이상 가속 알림

### 3.1 목적과 사용할 사람

차가 예상보다 빠르게 움직였을 때 당시의 상태를 남기고 위험을 알리는 앱이다. 급발진이 걱정되는 운전자와 가족을 대상으로 한다. 원인을 모르는 급가속을 처음부터 차량 결함이나 페달 착각으로 분류하지 않는다.

출발 전에는 자료 수집 상태를 확인한다. 주행 중에는 조작을 요구하지 않고 기록한다. 위험이 의심되면 짧은 표시나 알림을 내고 당시 기록을 보관한다. 경고음이 운전을 더 방해하는지는 별도로 시험해야 한다.

### 3.2 사용할 정보와 판단의 한계

첫 구성은 실제 차량 속도, 브레이크 입력 여부, 인식한 말, 위치다. 가속 페달 입력과 움직임 센서는 사용할 수 있을 때 더한다.

예를 들어 속도가 빠르게 늘어나는 동안 놀란 말이 인식되면 그 구간에 표시한다. 그러나 오르막·내리막, 합류를 위한 가속, 센서 오류도 구분해야 한다. ‘몇 초 안에 몇 km/h가 늘면 급발진’ 같은 값을 이번 조사로 확정할 수 없다.

브레이크가 ‘밟지 않음’으로 들어와도 가속 페달을 밟았다는 뜻은 아니다. 브레이크가 ‘밟음’으로 들어와도 실제 제동력이 충분히 발생했는지는 알 수 없다. 두 값이 함께 필요한 이유다.

### 3.3 필요한 화면

| 화면 | 보여 줄 것 | 사용자의 행동 |
| --- | --- | --- |
| A1. 출발 전 상태 | 속도·브레이크·음성·위치의 지원 여부와 마지막 수신 시각 | 정차 중 기록 시작과 공유 조건 확인 |
| A2. 주행 중 기록 | 기록 작동 여부와 중지된 항목 | 별도 입력 없이 확인 |
| A3. 위험 표시 | 감지한 자료와 시각, 현재 보관·전송 상태 | 주행 중 상세 입력을 요구하지 않음 |
| A4. 주행 후 확인 | 속도 변화, 브레이크 상태, 인식 문장, 위치를 같은 시간표에 표시 | 안전하게 정차한 뒤 기록 확인과 공유 |

### 3.4 ‘방지’하려면 더 필요한 것

차량을 실제로 멈추려면 가속 제한이나 브레이크 작동 기능이 필요하다. 이번에 확인한 공개 Vehicle SDK에는 해당 명령이 없다. 앱이 기어·크루즈 기능을 우회 조작해 급정지를 시도하는 방식도 제안하지 않는다.

현대차그룹은 이미 페달 오조작 안전 보조(PMSA)를 소개하고 있다. 차량의 센서와 제어 장치를 사용해 가속을 제한하거나 제동을 돕는 제조사 안전 기능이다. 공개 앱에서 같은 제어를 할 수 있다는 근거는 아니다. [현대차그룹 PMSA 자료](https://www.hyundaimotorgroup.com/ko/tag/pedal-misapplication-safety-assist)

공모전에서는 ‘급발진을 막는 장치’라는 성능을 주장하지 않는다. **이상 가속 상황을 알리고 자료를 보관하는 앱**으로 제시하고, 실제 가속 차단·제동은 제조사와 별도 개발할 단계로 명시한다.

## 4. 페달 확인 도우미

### 4.1 목적과 사용할 사람

브레이크와 가속 페달을 헷갈리는 문제를 줄이기 위한 확인·연습 앱이다. 운전을 다시 시작하는 사람이나 차량이 바뀐 운전자 등이 사용할 수 있다. 특정 나이만으로 실수를 단정하지 않는다.

페달 혼동은 미국 도로교통안전국의 기술 연구 목록에도 다뤄진 문제다. 다만 그 연구가 이 앱의 예방 효과를 입증하지는 않는다. [NHTSA 기술 연구 목록의 페달 오조작 연구](https://www.nhtsa.gov/crash-avoidance/office-crash-avoidance-research-technical-publications)

### 4.2 실제 차량에서는 무엇을 할 것인가

차를 안전하게 세운 상태에서 앱이 브레이크 입력을 읽을 수 있는지 보여 준다. 입력이 확인되면 ‘브레이크 입력 확인’, 값이 없으면 ‘브레이크 입력 확인 불가’라고 표시한다.

이 표시는 브레이크 성능 점검이나 출발 허가가 아니다. 브레이크를 밟았다는 신호를 읽었다는 뜻이다. 실제 차량에서 가속 페달을 밟게 하는 시험은 첫 버전에 넣지 않는다.

주행 중에는 브레이크 입력과 속도, 가능한 경우 가속 페달 비율을 기록한다. 가속 페달 비율을 받지 못하면 두 페달 중 무엇을 밟았는지 모두 알아낼 수 있다고 설명하지 않는다.

### 4.3 페달 연습은 어떻게 할 것인가

별도 모형 페달이나 시뮬레이터에서 화면의 지시에 따라 브레이크를 고르는 연습을 한다. 어느 페달을 눌렀는지와 반응 시간을 표시한다. 실제 차량을 움직여 연습하는 방식은 제외한다.

모형 페달이 보내는 값은 차량 SDK의 값과 구분한다. ‘연습 장치 입력’이라고 표시하고, 실제 차량 신호가 들어온 것처럼 시연하지 않는다.

### 4.4 필요한 화면

| 화면 | 보여 줄 것 | 사용자의 행동 |
| --- | --- | --- |
| B1. 출발 전 브레이크 확인 | 입력 여부·수신 시각·확인 불가 사유 | 정차 중 상태 확인 |
| B2. 모형 페달 연습 | 연습 지시와 실제 누른 모형 페달 | 연습 장치에서 선택 |
| B3. 연습 결과 | 선택 오류와 반응 시간 | 결과 확인. 실제 사고 위험 점수로 표시하지 않음 |
| B4. 주행 후 입력 기록 | 지원되는 페달·속도·음성 자료의 시간표 | 정차 후 확인 |

### 4.5 실제 오조작 차단으로 확장할 조건

가속 페달 비율이 확인되면 두 페달 입력을 더 자세히 볼 수 있다. 그래도 운전자가 무엇을 하려 했는지까지 알 수 있는 것은 아니다. 승인된 발밑 카메라나 추가 센서가 있으면 보조 자료로 검토할 수 있으나, 현재 제공 기능으로 확정하지 않는다.

페달 착각을 알아차려 가속을 차단하는 기능은 제조사의 안전 제어가 필요하다. 이 앱이 짧은 경고만으로 사고를 막는다고 보장할 수 없다. 실제 예방 효과는 반복 사용 시험과 별도 안전 검증이 필요하다.

## 5. 사고 기록과 보호자 알림

### 5.1 목적과 사용할 사람

사고 직전과 직후의 상황을 가족이 확인할 수 있도록 돕는 앱이다. 운전자가 휴대폰을 조작하기 어려운 상황에서 위치와 받은 사고 신호를 먼저 전달하는 것이 목적이다.

‘모든 기록’은 사용을 허용받아 실제로 받은 자료의 전체를 뜻하도록 범위를 적는다. 접근할 수 없는 카메라, 녹음이 시작되기 전의 소리, 전원이 꺼진 뒤의 상황을 복구할 수 있다고 설명하지 않는다.

### 5.2 평소부터 짧게 보관한다

사고 이전 기록을 남기려면 사고가 나기 전부터 기록해야 한다. 최근 자료를 짧게 보관하고 오래된 자료를 순서대로 지우는 방식을 제안한다. 사건이 생기면 해당 구간은 지우지 않는다.

첫 시연에서는 **사건 전 30초와 사건 후 60초**를 예시로 삼는다. 이 길이는 기획값이며 SDK가 보장한 시간이 아니다. 저장 공간·실행 지속 시간·음성 처리·차량 정책을 시험한 뒤 정한다. 시작한 지 10초 만에 사건이 발생하면 이전 10초만 보관하고 20초는 ‘기록 없음’으로 표시한다.

### 5.3 무엇을 사건으로 볼 것인가

| 상황 | 분류 | 처리 |
| --- | --- | --- |
| 사용자가 긴급 요청을 직접 실행 | 사용자 요청 | 우선 알림과 기록 보관 |
| 이전 상태와 비교해 새 에어백 전개 신호 수신 | 사고 관련 신호 | 음성·영상 분석을 기다리지 않고 알림과 보관 |
| 급격한 속도 변화와 놀란 말 등 여러 자료가 겹침 | 위험 상황 의심 | 근거를 붙여 보관하고, 사전 동의한 공유 규칙 적용 |
| 기울기나 흔들림만 관측 | 움직임 이상 의심 | 자료를 보관하되 전복·충돌로 확정하지 않음 |
| 놀란 말만 관측 | 확인이 필요한 말 | 표시와 기록 보관. 곧바로 사고 확정 알림을 보내지 않음 |

에어백이 펼쳐지지 않는 사고도 있을 수 있다. 앱을 켰을 때 이미 전개 상태가 참으로 들어왔다면 새 사고로 처리하지 않는다. 이전 상태와 새 알림, 수신 시각을 구분한다. 급제동이나 충격만으로 사고 원인을 확정하지 않는다.

‘사고 직전 감지’는 위험 징후가 들어온 구간을 찾는 뜻으로 사용한다. 충돌이 일어나기 전에 반드시 예측할 수 있다는 성능은 이번 조사에서 확인되지 않았다.

### 5.4 어떤 자료를 보관할 것인가

| 자료 묶음 | 보관할 내용 | 자료가 없을 때 |
| --- | --- | --- |
| 사건 설명 | 사건 번호, 시작 시각, 받은 신호, 분류, 앱 버전 | 원인을 추측해 채우지 않음 |
| 위치 | 좌표, 위치 시각, 정확도, 최근 이동 경로 | 마지막으로 받은 위치와 경과 시간 표시 |
| 차량 상태 | 속도, 브레이크 입력, 에어백, 핸들 각도와 지원되는 상태 | 항목별로 미지원·권한 거절·오류·수신 끊김 구분 |
| 움직임 | 사용할 수 있는 가속도·회전·기울기와 장치 방향 | 미지원 표시. 다른 값으로 임의 대체하지 않음 |
| 음성 | 인식한 문장, 중간·최종 구분, 결과 수신 시각 | 인식 꺼짐·실패·해당 구간 없음 표시 |
| 원본 소리 | 허용된 내부·외부 녹음이 있을 때 해당 구간 | ‘원본 녹음 없음’ 표시 |
| 영상 | 허용된 전방·후방·실내·발밑 영상이 있을 때 해당 구간 | 카메라별로 미지원·접근 불가·구간 없음 표시 |
| 작동 상태 | 전원·연결·저장·전송 오류와 자료의 마지막 수신 시각 | 기록의 빈 구간을 숨기지 않음 |

모든 자료를 같은 시계 기준으로 정렬한다. 장치가 제공한 시각과 앱이 받은 시각을 구분한다. 서로 시각을 맞추지 못한 자료는 오차를 표시한다. 녹음과 영상이 있다면 재생 위치와 차량 상태를 함께 볼 수 있게 한다.

### 5.5 보호자에게 무엇부터 보낼 것인가

처음에는 용량이 작은 사건 정보부터 보낸다. 사건 시각, 위치와 정확도, 실제 받은 신호, 자료가 없는 항목, 차량 앱의 마지막 연결 시각을 포함한다. 영상과 원본 소리는 허용된 자료가 있을 때 뒤이어 나눠 보낸다.

예를 들어 보호자에게 ‘14:03 에어백 전개 신호 수신. 마지막 위치 14:03. 차량 상태 전송 완료. 실내 영상 없음’이라고 표시할 수 있다. 이 문장은 가상 예시다.

아래 상태를 따로 기록한다.

1. 차량 안에 저장했다.
2. 서버로 전송을 시도했다.
3. 서버가 받았다.
4. 보호자 기기에 도착했다.
5. 보호자가 열어 봤다.

각 상태는 실제 확인 응답을 받았을 때만 표시한다. 알림 서비스를 호출한 것만으로 보호자가 받거나 읽었다고 표시하지 않는다.

통신이 끊기면 차 안에 나눠 저장하고 다시 연결되면 미전송 구간을 보낸다. 전원이 갑자기 끊기면 마지막 구간이 저장되지 않을 수 있다. 계속 연결되어 있지 않으면 실시간 전달도 보장할 수 없다. 마지막 수신 시각을 보호자 화면에 표시한다. [Pleos 통신·플랫폼 조건](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/platform-api-architecture)

### 5.6 등록과 공유 범위

보호자는 초대와 본인 확인을 거쳐 등록한다. 운전자는 위치, 인식한 말, 원본 녹음, 영상의 공유 범위를 각각 정한다. 평소 전체 이동 경로를 공유할지, 사건이 생긴 구간만 공유할지도 구분한다.

보관 기간과 삭제 방법, 등록 취소, 접속 기록을 제공한다. 사용자가 바뀌는 공유 차량에서는 이전 운전자의 자료가 다음 사용자에게 열리지 않게 한다. 원본 녹음과 영상은 동승자 등의 정보도 담을 수 있으므로 수집·공유 설명을 따로 마련해야 한다. 일괄적으로 녹음이 모두 허용된다고 판단하지 않는다. [Pleos 보안·개인정보 안내](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/security-privacy)

보호자가 운전자의 승인 없이 차량 마이크나 카메라를 원격으로 켜는 기능은 넣지 않는다. 보호자 알림은 별도 서버와 휴대폰 화면을 개발해야 하며, 기존 차량 긴급구조 서비스와 동일한 기능으로 설명하지 않는다.

### 5.7 필요한 화면

| 화면 | 보여 줄 것 | 사용자의 행동 |
| --- | --- | --- |
| C1. 보호자와 공유 설정 | 등록한 보호자, 공유 항목, 사건별 공유 조건, 보관 기간 | 정차 중 등록·변경·철회 |
| C2. 기록 상태 | 자료별 지원·권한·수신 상태, 기록 시작 시각 | 정차 중 기록 시작·중지 |
| C3. 사건 보관·전송 | 사건 종류, 저장 구간, 누락 항목, 전달 단계 | 운전 중 입력 없이 상태 확인 |
| C4. 보호자 휴대폰 | 사건 정보·위치·마지막 연결 시각·받은 자료 | 사건 열람과 수신 확인 |
| C5. 사건 다시 보기 | 시간에 맞춘 차량 정보·인식 문장·사용 가능한 영상과 소리 | 정차 후 검토·내보내기·삭제 |

## 6. 함께 만들 때의 구조와 개발 순서

### 6.1 한 앱에 넣는다면

사고 기록과 보호자 알림을 기본으로 만들고, 이상 가속 표시와 페달 확인을 보조 기능으로 두는 안을 권한다. 세 기능이 속도·브레이크·음성·위치의 같은 기록을 사용하기 때문이다. 이것은 개발 순서에 관한 판단이며 수상 가능성이나 수요를 검증한 결론은 아니다.

제안하는 구조는 다음과 같다.

1. **차량 앱:** 지원·권한 확인, 자료 수집, 사건 구간 보관, 알림 조건 적용.
2. **서버:** 등록 확인, 사건 정보와 허용된 파일 저장, 보호자 알림, 접속 기록.
3. **보호자 화면:** 위치와 자료 수신 상태 확인, 사건 열람, 수신 확인.
4. **시연용 입력:** 에뮬레이터와 별도 모형·시험 파일. 실제 수집 자료와 구분.

급한 판단과 구간 보관은 가능한 한 차량 안에서 처리한다. 인터넷 응답을 기다리다 기록이 지워지지 않게 하기 위해서다. 이것이 차량 앱의 지속 실행이나 무정전 기록을 보장한다는 뜻은 아니다.

### 6.2 확인 순서

| 순서 | 확인할 일 | 통과했다고 볼 증거 |
| --- | --- | --- |
| 1 | 대상 에뮬레이터에서 속도·브레이크·에어백·음성·위치 지원 확인 | 권한 결과, 지원 목록, 실제 수신값·시각·오류 기록 |
| 2 | 정상·오류·자료 없음 상태를 표시 | 자료가 없을 때도 값이 있는 것처럼 보이지 않는 화면 |
| 3 | 음성 예문과 여러 차량 신호를 시험 입력으로 재생 | 중복·누락·잘못된 알림 횟수와 알림 지연 측정 |
| 4 | 사건 전후 보관과 통신 끊김·앱 종료를 시험 | 남은 구간, 빠진 구간, 재전송·중복 처리 결과 |
| 5 | 보호자 등록·동의·철회·전달 상태를 시험 | 허용한 사람만 열람하고 전달 단계를 구분한 결과 |
| 6 | 원본 녹음·영상·움직임 센서의 공식 사용 경로 확인 | 장치·권한·실제 캡처 결과. 없으면 미지원으로 유지 |

음성 시험에는 운전자의 예문뿐 아니라 동승자 대화, 방송, 음악, 바람, 방언, 말이 겹치는 상황, 말이 전혀 없는 사고 신호를 포함한다. 차량 신호 시험에는 정상 가속, 급제동, 경사로, 자료 지연과 끊김을 포함한다. 움직임 센서를 쓰면 장치 흔들림과 장치가 떨어지는 경우도 구분해야 한다.

실차에서 급가속·충돌·페달 착각을 일부러 일으키는 시연은 제안하지 않는다. 첫 출품 시연은 에뮬레이터와 명확히 표시한 시험 입력으로 구성한다.

## 7. 위험, 미정 사항, 확인한 한계

### 7.1 먼저 해결해야 할 위험

| 우선순위 | 위험 | 기획에 반영한 대응 |
| --- | --- | --- |
| 높음 | 앱이 제동해 준다고 사용자가 믿음 | 자동 정지·가속 차단은 제공하지 않는다고 기능 설명에 명시 |
| 높음 | 놀란 말이나 급제동을 사고로 잘못 알림 | 말·속도·기타 신호를 구분해 보관하고 ‘의심’과 받은 사실을 구별 |
| 높음 | 영상·소리가 없는데 모두 기록했다고 표시 | 자료별 지원·권한·빠진 구간을 표시 |
| 높음 | 통신·전원·앱 종료로 사건 기록을 놓침 | 짧은 단위 저장, 재전송, 마지막 수신 시각, 누락 표시 |
| 높음 | 보호자에게 원치 않는 사적 대화나 이동 기록이 노출 | 항목별 동의·사건 구간 공유·접속 제한·철회와 삭제 |
| 보통 | 경고음·화면이 운전을 방해 | 주행 중 입력 최소화, 경고 빈도와 방해 정도 시험 |
| 보통 | 수집값만으로 운전자 과실이나 차량 결함을 단정 | 관측한 값과 해석을 구분하고 원인 판정 기능으로 설명하지 않음 |

파일의 변경 여부를 확인하는 식별값과 전송 기록을 남길 수는 있다. 그래도 이 앱의 자료를 공인 사고기록 장치나 사고 원인 판정 결과와 동일하게 취급할 수는 없다.

### 7.2 아직 정하지 않은 것

공모전 첫 버전에 보호자 휴대폰 앱까지 만들지, 휴대폰 웹페이지로 만들지는 미정이다. 사건 보관 기간, 음성만 인식했을 때의 공유 조건, 허용 가능한 잘못된 알림 횟수와 지연 시간도 사용자 시험 뒤 정해야 한다.

가속 페달·움직임·원본 소리·카메라를 사용할 수 없다면 기본 기능의 범위를 줄인다. 빈 자료를 추정값이나 시험 파일로 채워 실제 관측으로 표시하지 않는다. 자동 제동을 목표로 바꾸려면 제조사 안전 기능과 별도 개발이 필요하다.

### 7.3 자료 기준과 실제 수행

이전 [SDK 검토](pleos-sdk-review.md), [공모전 조사](hyundai-vehicle-app-contest-2026.md), [선택한 네 아이디어](selected-app-ideas-2026-11-12.md)를 먼저 참고했다. 작업 시작 시 이 폴더는 Git 저장소가 아니었으며 앱 소스·서버·APK는 없었다. 기존 파일의 시작 식별값은 이번 [확인 기록](../sdk/evidence/vehicle-safety-inspection-2026-11-12.json)에 남긴다.

2026-11-12에 공식 개발 문서와 차량·음성 SDK 배포 파일을 다시 읽었다. Vehicle 2.3.2의 차량 기능 인터페이스 20개에서 메서드 선언 517개를 정적으로 살폈다. 이 수는 중복 이름·이전 방식·권한 제한을 포함하므로 사용 가능한 기능 517개라는 뜻은 아니다. SpeechToText 3.3.1에서는 주 클래스와 결과 전달 인터페이스를 확인했다.

실제 음성 인식, 에뮬레이터 연결, 센서 조회, 영상·소리 저장, 알림 전송, 앱 지속 실행, 실차·사고·예방 효과는 시험하지 않았다. 이번 결과는 기능 근거 조사와 기획 문서다. 지원되지 않는 기능을 제공한다고 표시하거나 보호자에게 실제 알림을 보내지 않았다.

후속 작업은 이 문서와 [SDK 기능 조사](../sdk/vehicle-safety-capabilities.md)를 먼저 읽고, 새로 확인한 기능과 시험 결과를 해당 부분에 갱신한다. 다른 아이디어의 기존 기획은 [네 아이디어 문서](selected-app-ideas-2026-11-12.md)에 유지한다. 공통 안내는 [AGENTS.md](../../AGENTS.md)에 기록한다.
