# 차량용 앱 아이디어 네 가지 구체화

작성일: **2026-11-12, 한국 시간**.

전체 비교는 [여섯 아이디어 요약](six-app-ideas-2026-11-12.md)에 정리했습니다. 이 문서에는 기존 네 아이디어의 상세 내용을 유지합니다.

선택한 아이디어는 세이브포인트, 경고등 도감, 귀가 역전골, 반찬 입국심사다. 각 앱을 누가 쓰는지, 무엇을 누르는지, 어떤 화면이 필요한지 정리한다.

이 문서의 기능과 화면은 앞으로 만들 안이다. 앱을 만들거나 차에서 실행한 결과는 아니다. 예시의 사람, 장소, 시각은 설명을 위해 정한 값이다.

이후 요청한 급가속 대응·페달 확인·사고 기록은 [세 가지 안전 앱 문서](vehicle-safety-app-ideas-2026-11-12.md)에 추가했다. 해당 SDK 조사에서 경고 표시의 단발 조회와 변경 알림의 권한이 다른 점도 확인했다. 경고등 도감의 자동 연결을 확장할 때 [안전 기능 조사](../sdk/vehicle-safety-capabilities.md)를 먼저 확인한다. 이 추가 조사는 아래 네 앱의 실행 결과가 아니다.

| 앱 | 하는 일 | 사용자가 마치는 일 |
| --- | --- | --- |
| 세이브포인트 | 차에서 적은 주차 정보를 휴대폰으로 옮긴다. | 주차한 곳을 확인하고 차로 돌아온다. |
| 경고등 도감 | 차종에 맞는 경고등 설명을 찾는다. | 표시의 뜻과 공식 안내를 확인한다. |
| 귀가 역전골 | 동승자가 내릴 장소와 운전자의 귀가 계획을 함께 정한다. | 두 하차 장소를 거쳐 운전자의 목적지로 간다. |
| 반찬 입국심사 | 냉장할 음식을 차에 싣고 내린 뒤 보관할 때까지 기록한다. | 음식을 냉장고에 넣고 완료 표시를 한다. |

공통 원칙은 세 가지다. 입력과 계획 변경은 차를 세운 뒤 한다. 기계가 확인하지 못한 일은 사람이 확인한다. 위치나 통신이 없을 때 완료한 것처럼 표시하지 않는다.

## 1. 세이브포인트

**차에서 내리기 전에 주차한 곳을 적고, 휴대폰에서 다시 보는 앱이다.**

### 1.1 사용할 사람과 상황

큰 주차장이나 처음 방문한 건물에서 차를 찾기 어려운 사람을 대상으로 한다. 운전자가 주차를 마친 바로 그때 기록한다. 주차장을 떠난 뒤 기억을 되짚어 적는 일을 줄이는 것이 목적이다.

예시는 지하 3층, 보라색 기둥, 42번 자리다. 실내에서는 지도 위의 점만으로 층과 자리를 알기 어렵기 때문에 글로 적은 정보가 필요하다.

### 1.2 사용 순서

1. 차를 세운 뒤 앱을 연다.
2. 앱이 받은 위치와 위치를 받은 시각을 확인한다. 위치가 없으면 메모만 적는다.
3. 주차장 이름, 층, 구역, 자리 번호를 적는다. 모르는 항목은 비워 둘 수 있다.
4. 주차 정보를 저장한다.
5. 휴대폰 카메라로 읽는 그림인 QR코드를 열어 기록을 휴대폰에 옮긴다.
6. 돌아올 때 휴대폰에서 주차 정보를 확인한다.
7. 차에 돌아오면 차량 화면에서 차량을 찾았다고 표시한다.

위치는 주차 정보를 돕는 자료다. 층이나 주차면 번호를 자동으로 알아내는 기능은 첫 버전에 넣지 않는다.

### 1.3 필요한 화면

| 화면 | 표시할 내용 | 사용자가 하는 일 |
| --- | --- | --- |
| S1 주차 정보 입력 | 주차장, 층, 구역, 자리 번호, 메모, 위치 확인 시각 | 내용을 적고 저장한다. |
| S2 저장 결과 | 저장한 정보, QR코드, 위치 유무 | 내용을 고치거나 휴대폰으로 옮긴다. |
| S3 차량의 최근 기록 | 현재 남아 있는 주차 기록 한 건 | 차량 찾음 또는 기록 삭제를 누른다. |
| S4 휴대폰 주차 카드 | 옮긴 메모, 저장 시각, 위치가 있으면 지도에서 볼 수 있는 정보 | 주차한 곳을 확인하고 휴대폰 기록을 지운다. |

슬라임은 저장한 자리에서 기다리는 캐릭터로 사용한다. 차량 찾음을 누르면 짧은 인사를 보여준다. 주행 거리나 속도를 점수로 바꾸는 기능은 넣지 않는다.

### 1.4 저장할 정보

| 정보 | 입력 방법 |
| --- | --- |
| 주차장 이름 | 직접 입력하거나 이전 이름을 선택한다. |
| 층, 구역, 자리 번호 | 직접 입력한다. |
| 추가 메모 | 필요할 때만 적는다. |
| 위치와 위치 확인 시각 | 차량 위치 기능에서 받는다. 없으면 위치 없음으로 저장한다. |
| 저장 시각 | 앱이 기록한다. |
| 기록 상태 | 저장 중, 저장 완료, 차량 찾음으로 구분한다. |

저장 버튼을 누른 시각과 위치를 받은 시각은 따로 남긴다. 예전에 받은 위치를 방금 확인한 위치처럼 보여주지 않는다.

### 1.5 첫 버전의 범위

- 현재 주차 기록 한 건을 저장하고 고친다.
- QR코드로 휴대폰에 기록을 복사한다.
- 휴대폰에서 기록을 다시 열 수 있게 한다.
- 차에 돌아온 뒤 기록을 끝내거나 지운다.
- 짧은 슬라임 동작을 보여준다.

휴대폰용 작은 웹페이지는 별도로 만들어야 한다. 첫 안은 주차 정보를 휴대폰에 복사하는 방식이다. 차와 휴대폰의 기록을 항상 같게 맞추는 기능은 넣지 않는다. 차에서 기록을 지워도 이미 복사한 휴대폰 기록은 별도로 지워야 한다.

### 1.6 실패할 때의 처리

| 상황 | 처리 방법 |
| --- | --- |
| 지하에서 위치를 받지 못함 | 메모 저장은 허용하고 위치 없음으로 표시한다. |
| 위치를 받은 지 오래됨 | 받은 시각을 보여주고 사용자가 확인하게 한다. |
| QR코드를 읽지 못함 | 저장한 메모를 계속 보여준다. 휴대폰 연결 실패를 저장 성공과 구분한다. |
| 휴대폰 웹페이지를 처음 열 수 없음 | 휴대폰으로 옮기기 완료 표시를 하지 않는다. |
| 다른 사람이 QR코드를 읽음 | 기록을 볼 수 있으므로 필요한 정보만 담고, 사용자가 요청할 때만 코드를 보여준다. |

실내 보행 길찾기, 주차장 빈자리 찾기, 주차 요금 결제는 첫 버전의 범위에서 뺀다.

### 1.7 차에서 쓸 이유와 남은 질문

Google 지도에도 주차 위치와 층수 메모를 저장하는 기능이 있다. 따라서 주차를 기록한다는 사실만으로 새로운 앱이 되지는 않는다. 이 안에서는 차에서 내리기 전에 기록을 끝내고 휴대폰으로 가져가는 과정이 더 편한지 확인해야 한다. [Google 공식 안내](https://support.google.com/maps/answer/7257797?co=GENIE.Platform%3DAndroid&hl=en)

첫 비교에서는 같은 주차 메모를 휴대폰에 직접 적는 방법과 차량에서 옮기는 방법을 사용하게 한다. 기록 시간, 잘못 옮긴 항목, 나중에 다시 열 수 있는지를 본다. 아직 이런 비교를 한 결과는 없다.

### 1.8 시연에서 보여줄 것

지하 주차장 메모 한 건을 입력하고, 실제 위치가 없는 경우도 함께 보여준다. QR코드로 휴대폰에 옮긴 후 페이지를 닫았다가 다시 열어 같은 기록이 남는지 확인한다. 차에서 차량 찾음을 누르는 장면까지 연결한다. 지도에서 실내 길을 찾아준 것으로 설명하지 않는다.

## 2. 경고등 도감

**후속 변경:** 이 아이디어는 이상 가속·사고 대응과 [하나의 Pleos 앱](integrated-vehicle-care-2026-11-12.md)으로 통합했습니다. 지원 Pleos 차량의 전체 경고등·표시등·경고문구, 직접·사진 찾기, 정비소 연결, 순간 증상 기록이 현재 요구사항입니다. 아래의 세 항목 한정안은 통합 전 이력입니다.

**차종과 표시 상태에 맞는 공식 경고등 설명을 찾는 앱이다.**

### 2.1 사용할 사람과 상황

경고등의 모양과 뜻이 낯선 운전자를 대상으로 한다. 차를 세운 뒤 눈앞의 표시와 앱의 그림을 비교한다. 표시의 모양을 검색어로 설명하는 일을 줄이는 것이 목적이다.

첫 버전은 한 차종의 세 항목만 다룬다. 안전벨트, 연료 부족, 타이어 공기압이다. 현재 확인한 한국어 자료는 현대차의 2026년형 DN8HEV 설명서다. 이는 설명 자료를 고른 기준이며, 공모전 에뮬레이터나 사용자의 차가 해당 모델이라는 뜻은 아니다. [한국어 공식 설명서](https://ownersmanual.hyundai.com/full_webhelp/DN8HEV/2026/ko_KR/warning_indicator_lights.html)

### 2.2 사용 순서

1. 차량의 모델, 연식, 판매 지역을 확인한다.
2. 차를 세운 뒤 표시된 경고등과 같은 그림을 고른다.
3. 언제 켜졌는지, 계속 켜져 있는지, 깜박였는지 선택한다.
4. 해당 조건에 맞는 짧은 설명을 읽거나 듣는다.
5. 정확한 내용과 행동은 연결된 공식 설명서에서 확인한다.

표시를 잘 모르거나 맞는 차종의 자료가 없으면 설명을 확정하지 않는다. 비슷한 다른 차종의 설명으로 대신하지 않는다.

### 2.3 필요한 화면

| 화면 | 표시할 내용 | 사용자가 하는 일 |
| --- | --- | --- |
| W1 차량 확인 | 모델, 연식, 판매 지역, 자료 확인일 | 자기 차와 맞는지 확인한다. |
| W2 경고등 선택 | 첫 버전의 경고등 그림 세 개와 이름 | 같은 표시를 고르거나 잘 모르겠음을 선택한다. |
| W3 표시 상태 | 켜진 시점, 계속 켜짐, 깜박임, 상태 모름 | 직접 본 상태를 고른다. |
| W4 설명 | 공식 이름, 선택한 상태, 뜻, 공식 안내, 원문 주소 | 설명을 읽고 원문 보기나 읽어주기를 선택한다. |

화면의 색만 보고 운행 가능 여부를 판정하지 않는다. 꺼짐과 고장 해결도 같은 뜻으로 취급하지 않는다.

### 2.4 설명 카드에 넣을 내용

| 항목 | 작성 기준 |
| --- | --- |
| 표시 이름 | 해당 차종의 공식 이름을 사용한다. |
| 적용 차량 | 모델, 연식, 판매 지역을 함께 적는다. |
| 선택한 상태 | 사용자가 고른 시점과 표시 방식을 보여준다. |
| 뜻 | 원문에서 확인한 내용을 짧게 풀어 쓴다. |
| 해야 할 일 | 공식 안내의 조건과 주의사항을 빼지 않고 작성한다. |
| 자료 | 원문 링크와 마지막 검토일을 남긴다. |

타이어 표시는 공기압 부족과 감지 장치 이상을 구분해야 한다. 계속 켜지는 경우와 깜박인 뒤 켜지는 경우를 같은 설명으로 합치지 않는다. 안전벨트와 연료 부족도 해당 차량 설명서의 조건을 따른다. 구체적인 정비 방법을 새로 만들어 넣지 않는다.

### 2.5 첫 버전의 범위

- 한 차종의 경고등 세 개를 찾는다.
- 사용자가 본 표시 상태를 직접 고른다.
- 미리 검토한 설명을 읽거나 음성으로 듣는다.
- 인터넷이 없어도 저장된 설명은 읽는다. 원문 웹페이지 열기는 통신이 필요하다.
- 자료가 없거나 입력이 부족하면 확인할 수 없다고 표시한다.

켜진 경고등을 차량에서 자동으로 받아 고르는 기능은 뒤에 검토한다. 어떤 신호를 읽을 수 있는지, 실제 표시와 정확히 맞출 수 있는지 먼저 확인해야 한다. 초기 화면에 시험값을 넣는 경우에는 실제 차에서 받은 값처럼 표시하지 않는다.

### 2.6 캐릭터와 수집 요소

도감이라는 이름은 설명을 찾아보기 쉽도록 붙인 것이다. 경고가 있는 동안 점수, 퀴즈, 수집 축하 화면을 먼저 보여주지 않는다. 표시를 많이 켜거나 위험한 상황을 만들어 보상을 받는 규칙도 넣지 않는다.

그림과 설명의 이용 조건은 확인해야 한다. 모든 차종의 설명서를 임의로 모아 배포하는 것을 첫 버전의 전제로 삼지 않는다.

### 2.7 차에서 쓸 이유와 남은 질문

운전자가 실제 표시를 보고 있는 자리에서 자기 차에 맞는 설명을 확인할 수 있다. 다만 차량 자체에도 안내가 있을 수 있으므로, 새 앱을 열어야 더 편한지 확인해야 한다.

먼저 표시 선택과 조건에 따른 설명이 정확한지 검토한다. 사람이 이해하기 쉬워졌는지는 그다음에 확인한다. 확인할 수 없는 상태를 문제없음으로 잘못 보여주지 않는 것도 중요하다.

### 2.8 시연에서 보여줄 것

같은 타이어 표시를 골라도 상태 선택에 따라 다른 설명이 나오는 장면을 보여준다. 잘 모르겠음과 지원하지 않는 차종에서는 안내를 확정하지 않는 장면도 포함한다. 이는 설명 찾기의 시연이며 고장 진단이나 수리 성공의 시연이 아니다.

## 3. 귀가 역전골

**동승자가 내릴 장소를 먼저 합의하고, 운전자의 귀가 목표와 함께 내비에 넣는 앱이다.**

### 3.1 사용할 사람과 상황

운동 모임이나 야간 모임을 마친 뒤 같은 차를 타는 사람들을 대상으로 한다. 동승자는 집에 돌아갈 방법을 정하고, 운전자는 자신의 일정이 언제 끝날지 확인해야 한다.

첫 버전은 운전자가 직접 고른 하차 장소 두 곳과 마지막 목적지 한 곳을 다룬다. 가장 좋은 경로를 자동으로 찾아주는 서비스로 정하지 않는다.

### 3.2 사용 예시

아래 시각은 계산을 설명하기 위한 예시다. 실제 내비에서 받은 결과가 아니다.

| 항목 | 예시 |
| --- | --- |
| 출발 준비 시각 | 22:10 |
| 운전자 귀가 목표 | 22:50 |
| 동승자 | A와 B는 첫 번째 역, C는 두 번째 역에서 하차 |
| 방문 순서 | 첫 번째 역 → 두 번째 역 → 운전자 목적지 |
| 내비가 22:42 도착을 예상한 경우 | 목표보다 8분 일찍 도착할 것으로 표시 |
| 이후 내비가 22:56 도착을 예상한 경우 | 목표보다 6분 늦게 도착할 것으로 표시 |

도착 예상이 늦어지면 다음 정차 때 계획을 다시 정한다. 귀가 목표 시각을 고치거나, 모두 동의한 다른 하차 장소를 선택한다. 목표를 지키기 위해 속도를 높이라고 안내하지 않는다.

### 3.3 사용 순서

1. 운전자의 마지막 목적지와 귀가 목표 시각을 적는다.
2. 동승자별로 내릴 장소를 고른다.
3. 하차 장소가 두 곳을 넘으면 첫 버전에서는 계획을 확정하지 않는다.
4. 운전자가 방문 순서를 정하고 함께 확인한다.
5. 하차 장소 두 곳과 마지막 목적지를 내비에 보낸다.
6. 내비에서 경로를 받으면 현재 경로와 도착 예상 정보를 확인한다.
7. 도착 신호와 실제 하차 확인을 구분해 표시한다.

동승자 이름은 실제 이름 대신 A, B 같은 표시로 사용할 수 있다. 좌석 센서로 탑승자나 하차 완료를 알아낸다고 가정하지 않는다.

### 3.4 필요한 화면

| 화면 | 표시할 내용 | 사용자가 하는 일 |
| --- | --- | --- |
| R1 운전자 계획 | 마지막 목적지, 귀가 목표 시각 | 목적지와 시간을 적는다. |
| R2 하차 장소 | 동승자 표시, 내릴 장소 두 곳 | 각자 내릴 곳을 정한다. |
| R3 출발 전 확인 | 방문 순서, 최종 목적지, 확인 결과 | 순서를 바꾸거나 경로 보내기를 누른다. |
| R4 귀가 진행 | 현재 경로, 받은 정보의 시각, 목표와 예상의 차이, 하차 확인 | 정차 후 계획을 고치거나 하차를 확인한다. |

첫 버전은 차량 화면에서 함께 정하는 방식이다. 동승자 휴대폰 가입, 자동 연락, 실시간 위치 공유는 필수 기능으로 넣지 않는다.

### 3.5 내비 정보로 할 수 있는 일과 확인할 일

공식 문서는 경유지를 최대 두 개로 안내하고, 최종 목적지와 경유지를 묶어 경로를 요청하는 방법을 제공한다. 이 구조에 맞춰 첫 버전의 하차 장소도 두 곳으로 정했다. [경유지 안내](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/waypoint-settings), [경로 요청](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/route-with-waypoints)

개발 문서에는 목적지의 남은 시간 정보와 관련 알림이 있다. 다만 사용 중인 내비에서 어떤 값이 오는지, 시간 단위가 무엇인지, 언제 새 값이 오는지는 실제로 확인해야 한다. 확인 전에는 앱 안의 도착 시각 계산을 구현 완료로 적지 않는다. [SDK 변경 기록](https://document.pleos.ai/docs/pleos-only/release-note/sdk-release-note)

예상 정보를 받지 못하면 시간 확인 불가로 표시한다. 이전 값을 계속 최신 정보처럼 보여주지 않는다. 내비 기본 화면에서 시간을 확인하는 방법도 남긴다.

### 3.6 막차 정보는 별도로 다룬다

서울교통공사의 공개 자료는 1~8호선 역별 시간표다. 실제 열차 도착 시각과 다를 수 있다. 막차를 탈 수 있다고 보장하는 계산에 바로 사용하지 않는다. [막차 시간표 자료](https://data.seoul.go.kr/dataList/OA-110/A/1/datasetView.do)

첫 버전은 하차 장소와 귀가 목표를 합의하는 일부터 다룬다. 막차 안내를 붙일 때는 날짜, 노선, 방향, 역, 시간표 출처를 정확히 맞춰야 한다. 역 앞에서 승강장까지 걷는 시간과 환승도 별도 문제다.

### 3.7 실패할 때의 처리

| 상황 | 처리 방법 |
| --- | --- |
| 경로 요청이 실패함 | 계획을 저장하되 길 안내가 시작됐다고 표시하지 않는다. |
| 경로 찾기 완료 신호가 옴 | 길을 계산한 것으로만 표시한다. 하차 완료로 바꾸지 않는다. |
| 역 근처에 도착 신호가 옴 | 실제 하차 여부는 사람이 확인한다. |
| 도착 예상 정보를 받지 못함 | 시간 확인 불가로 표시한다. |
| 목표 시각이 지남 | 다음 정차 때 계획을 다시 정할 수 있게 한다. |

경로 계산 완료, 목적지 도착, 경유지 도착은 서로 다른 알림이다. 모두가 내렸는지 알려주는 신호는 아니다. [내비 알림 안내](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/event-listeners)

### 3.8 시연에서 보여줄 것

동승자 세 명을 하차 장소 두 곳에 나누고, 운전자의 마지막 목적지를 넣는다. 실제로 내비에 경로를 요청한 결과와 실패 결과를 구분해 보여준다. 시간 정보가 아직 연결되지 않았다면 예시 시각이라고 표시한 값으로 계산만 설명한다. 실제 내비 값을 받은 것처럼 설명하지 않는다.

## 4. 반찬 입국심사

**차에 실은 음식을 내리고 냉장고에 넣을 때까지 확인하는 앱이다.**

### 4.1 사용할 사람과 상황

부모님 집에서 반찬을 받아오거나, 냉장할 케이크와 음식을 차로 가져가는 사람을 대상으로 한다. 도착 후 인사와 다른 짐 정리에 밀려 음식을 차에 남기는 일을 줄이는 것이 목적이다.

첫 예시는 국 한 통과 반찬 한 통이다. 냉장이 필요한지는 사용자가 포장 표시나 제공자의 안내를 보고 정한다. 음식 이름만 보고 앱이 자동으로 판단하지 않는다.

### 4.2 확인하는 세 단계

| 단계 | 뜻 | 확인 방법 |
| --- | --- | --- |
| 차에 실음 | 음식을 차량에 가져왔다. | 사용자가 음식 목록을 저장한다. |
| 차에서 내림 | 음식을 차 밖으로 옮겼다. | 사용자가 직접 표시한다. |
| 냉장고에 넣음 | 집 안에서 보관을 마쳤다. | 휴대폰에서 사용자가 표시한다. |

목적지에 도착한 것만으로 음식 보관이 끝난 것으로 표시하지 않는다. 차에서 내렸다는 표시도 냉장고 보관 완료와 구분한다.

### 4.3 사용 순서

1. 출발 전에 음식 이름과 수량을 적는다.
2. 냉장할 음식인지, 보냉 준비를 했는지 직접 확인한다.
3. 냉장고에서 꺼낸 시각을 알면 적는다. 모르면 시간 모름으로 남긴다.
4. 앱이 기록을 저장한 시각을 따로 남긴다.
5. 목적지나 경유지가 바뀌어도 아직 보관하지 않은 음식 목록을 유지한다.
6. 목적지에 도착해 차를 세우면 내릴 음식 목록을 확인한다.
7. QR코드로 휴대폰 체크리스트를 열고, 음식을 내린 뒤 냉장고에 넣었는지 표시한다.

앱을 켠 시각을 음식이 냉장고에서 나온 시각으로 바꾸지 않는다. 경과 시간을 표시하더라도 어떤 시각부터 센 값인지 함께 적는다.

### 4.4 필요한 화면

| 화면 | 표시할 내용 | 사용자가 하는 일 |
| --- | --- | --- |
| F1 음식 등록 | 이름, 수량, 냉장 필요 여부, 꺼낸 시각 또는 시간 모름, 보냉 준비 확인 | 음식을 적고 직접 확인한다. |
| F2 이동 중 목록 | 남은 음식 수, 저장 시각, 현재 목적지 | 출발 전 준비를 확인하고, 변경 사항은 정차 후 고친다. |
| F3 도착 후 확인 | 차에서 내릴 음식, 단계별 상태, QR코드 | 내린 음식을 표시하고 휴대폰 화면을 연다. |
| F4 휴대폰 보관 확인 | 같은 음식 목록, 차에서 내림, 냉장고에 넣음, 전송 상태 | 보관한 음식을 표시한다. |

음식 목록은 짧게 읽어줄 수 있다. 첫 버전은 음식을 촬영하거나 냉장고를 자동으로 확인하는 기능에 의존하지 않는다.

### 4.5 차와 휴대폰의 기록

냉장고에 넣는 일은 차 밖에서 일어나므로 휴대폰 확인 화면이 필요하다. 휴대폰에서 완료한 내용을 차량 기록에도 반영하려면 두 화면 사이에서 내용을 전달하는 서버가 필요하다. 서버는 두 기기 사이의 기록을 전달하는 프로그램이다.

첫 안은 이름, 수량, 입력 시각, 완료 상태만 전달한다. 집 주소와 차량 이동 기록을 휴대폰 음식 목록에 넣을 필요는 없다. QR코드는 사용자가 요청할 때 열고, 사용을 마친 기록의 연결은 닫는 방식으로 검토한다.

통신이 끊기면 전송 대기로 표시한다. 상대 화면에 반영되지 않은 상태를 전송 완료로 보여주지 않는다. 실제 사람이나 가족에게 자동 메시지를 보내는 기능은 첫 버전에 넣지 않는다.

### 4.6 음식 안전을 판정하지 않는 이유

FDA는 냉장이 필요한 음식을 신속하게 보관하고 차량 안에 오래 두지 않도록 안내한다. 하지만 이 앱은 음식 속 온도, 보냉 상태의 실제 변화, 차에 싣기 전의 보관 이력을 알지 못한다. [FDA 공식 안내](https://www.fda.gov/food/buy-store-serve-safe-food/refrigerator-thermometers-cold-facts-about-food-safety)

따라서 첫 화면에 먹어도 됨, 안전까지 남은 시간, 음식이 상함 같은 판정을 넣지 않는다. 보냉 가방을 선택했다고 안전한 시간이 늘어났다고 계산하지도 않는다. 차량 실내 온도를 음식 내부 온도로 대신하지 않는다.

이 앱이 확인하는 것은 사람이 해야 할 일을 표시했는지 여부다. 실제 보관 상태를 센서로 확인하거나 식중독 예방 효과를 증명한 것은 아니다.

### 4.7 실패할 때의 처리

| 상황 | 처리 방법 |
| --- | --- |
| 꺼낸 시각을 모름 | 임의로 채우지 않고 시간 모름으로 남긴다. |
| 목적지가 바뀜 | 보관하지 않은 목록을 계속 남긴다. |
| 도착 신호가 없음 | 사용자가 정차 후 도착 확인 화면을 직접 연다. |
| 음식 일부만 내림 | 남은 항목만 유지한다. |
| 휴대폰 전송 실패 | 차량 목록을 지우지 않고 실패 상태를 표시한다. |
| 휴대폰에서 완료했지만 차량에 전달되지 않음 | 두 화면의 상태가 다를 수 있음을 표시하고 다시 전송한다. |

### 4.8 시연에서 보여줄 것

국 한 통과 반찬 한 통을 등록한다. 경유지를 추가해도 음식 목록이 남는 장면을 보여준다. 도착 후 한 통만 내렸을 때 다른 한 통이 남는지도 확인한다. 휴대폰에서 두 음식을 냉장고에 넣었다고 표시한 후 차량 기록이 바뀌는 장면까지 연결한다. 화면의 완료 표시는 사람의 확인이며 실제 냉장고를 감지한 결과가 아니다.

세이브포인트와 반찬 입국심사는 차에서 적은 내용을 휴대폰에서 이어 쓴다. 경고등 도감은 자료의 정확성이 중요하다. 귀가 역전골은 내비가 주는 정보의 범위를 먼저 확인해야 한다. 어느 앱을 먼저 만들지는 이 문서에서 확정하지 않는다.

## 6. 개발할 때 참고할 내용

SDK는 앱이 차량 기능을 가져다 쓸 때 사용하는 개발 도구다. API는 그 도구에 필요한 일을 요청하는 기능이다. 아래는 사용할 후보이며 실행 완료 목록이 아니다.

FusedLocation은 차의 위치를 받는 도구다. NaviHelper는 차의 내비에 목적지와 경유지를 보낸다. Vehicle은 허용된 차량 상태를 읽는다. TTS는 글을 소리로 읽고, STT는 말을 글로 바꾼다.

| 앱 | 사용할 후보 | 새로 만들 부분 | 확인할 조건 |
| --- | --- | --- | --- |
| 세이브포인트 | FusedLocation 1.1.3, 선택적으로 STT 3.3.1 | 주차 메모 저장, QR코드, 휴대폰 웹페이지 | 위치 허용, 위치의 시각, 휴대폰 보관 |
| 경고등 도감 | TTS 3.3.1, 확장 시 Vehicle 2.3.2 | 차종별 자료, 표시 상태 선택, 조건에 맞는 설명 | 정확한 원문, 그림 이용, 차량 신호 대응 |
| 귀가 역전골 | NaviHelper 3.0.5, 필요 시 FusedLocation 1.1.3 | 동승자·장소 입력, 방문 순서, 목표 시각 비교 | 경로 요청, 시간 정보, 실제 도착 알림 |
| 반찬 입국심사 | NaviHelper 3.0.5, TTS 3.3.1 | 음식 목록, 단계별 기록, 휴대폰 확인, 서버 전달 | 내비 변화, 통신 실패, 수동 완료 |

위치는 값이 없거나 오래된 값일 수 있다. 권한을 적었다는 사실만으로 허용이 끝나는 것도 아니다. [위치 정보](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/location-data-access), [위치 권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/declaring-permissions)

기존 SDK 검토에서는 Java 예제의 인자 수와 좌표 순서, 일부 콜백 이름이 실제 배포 파일과 다른 점을 확인했다. 예제를 그대로 옮기지 않고 사용할 버전과 맞춰야 한다. 이번 구체화에서는 새 배포 파일을 내려받거나 앱을 컴파일하지 않았다. [SDK 검토 기록](pleos-sdk-review.md)

주행 중 조작 제한과 정차 상태를 확인하는 방법은 실제 개발 환경에서 시험해야 한다. 내비의 도착 신호나 주차 브레이크 신호 하나만으로 모든 정차 조건이 충족됐다고 판단하지 않는다. 첫 시연은 차를 세운 상황으로 제한한다.

## 8. 이번 작업과 남은 확인

기존 [30개 아이디어](app-ideas-brainstorm-2026-11-11.md), [처음 작성한 주차·경고등 기록](brainstorm/2026-11-11/p08.md), [귀가 기록](brainstorm/2026-11-11/p02.md), [음식 기록](brainstorm/2026-11-11/p05.md), [SDK 검토](pleos-sdk-review.md)를 읽고 해당 부분을 구체화했다. 사용자 요청에 따라 반찬 입국심사를 네 번째로 추가했다.

작업 시작 시 이 폴더는 Git 저장소가 아니었고 Kotlin·Java 앱 소스는 없었다. 이번에도 앱 코드, 서버, 휴대폰 화면, APK를 만들지 않았다. 만든 것은 기능·화면·이용 순서에 관한 문서다.

먼저 확인할 작업은 다음과 같다.

1. 세이브포인트의 기록이 차량에서 휴대폰으로 옮겨지고 다시 열리는지 확인한다.
2. 경고등 세 항목의 조건·설명·공식 링크를 사람이 검토한다.
3. 귀가 앱이 필요한 남은 시간과 경로 알림을 실제로 받을 수 있는지 확인한다.
4. 음식 보관 완료가 휴대폰과 차량에 잘 전달되고, 실패가 구분되는지 확인한다.

이 네 작업을 완료했다고 표시하지 않는다. 사용자 인터뷰, 화면 시험, SDK 호출, 에뮬레이터, 실차, 내비·위치·음성, 식품 온도, 외부 API 인증은 시험하지 않았다.

확인한 원문 주소, 기존 문서의 파일 식별값, 제안한 화면 16개와 예시 계산값은 [확인 기록](selected-app-ideas-2026-11-12-evidence.json)에 남긴다. 공모전 공지는 웹 도구에서 자주 열리지 않아 직접 HTTP 읽기로 확인했다. 단일 URL 도구의 결과는 weak_ok였으며 이를 전체 개발 검증 완료로 해석하지 않는다.

문서 검사에서는 선택한 앱 네 개, 화면 번호 16개, 읽은 자료 12개와 제외한 후보 한 개를 대조했다. 파일 링크 오류는 없었다. 예시의 8분과 6분 계산도 확인했다. 이 결과는 문서 검사이며 앱이 작동한다는 결과는 아니다.
