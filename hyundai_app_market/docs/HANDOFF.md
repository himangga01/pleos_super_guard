## 1. 현재 상태부터 확인합니다

**공식 양식 14쪽과 상세 기획·기술 명세 40쪽의 Word·PDF가 완성돼 있습니다.** 공식 양식의 2~6번은 각각 Microsoft Word의 공백 포함 문자 수 기준으로 정확히 3,000자입니다. 두 문서를 묶은 ZIP도 최신 파일로 갱신했습니다.

완료된 것은 조사·기획·인터페이스 설계·화면 이미지·제출 문서입니다. 실제 차량용 앱, 안드로이드 보조 앱, API 서버는 아직 구현하지 않았습니다. 센서·블랙박스·카카오톡·문자·휴대폰 인계를 실제로 실행한 결과도 없습니다. 설계 문서와 문서 제작 스크립트를 실행 가능한 앱으로 소개하면 안 됩니다.

인계 작성 시 최종 파일 5개의 SHA-256이 기존 검증 기록과 일치하는지 다시 확인했습니다. PDF 쪽수도 다시 읽었습니다. Git 조회 결과 현재 폴더와 상위 폴더는 Git 저장소가 아니었습니다. 앱 프로젝트를 나타내는 Kotlin 파일, Gradle 파일, `package.json`도 발견하지 못했습니다. 이번 인계에서는 외부 공고·SDK 문서를 새로 조회하거나 Word·PDF를 다시 수정하지 않았습니다.

## 4. 사용자가 확정한 요구사항

### 서비스 범위

- 앱 이름은 **플레오스 가드**입니다. 옛 작업명인 차안심·차량안내를 현재 제품명으로 되돌리지 않습니다.
- Pleos가 탑재된 차량만 대상으로 합니다. Pleos 차량 앱이 주제품이며 안드로이드 휴대폰은 그 차량의 백업·보조 입력을 맡습니다.
- 기존 아이디어 2·5·6번을 통합했습니다. 경고등 도감, 순간 고장 증상 기록, 긴급 행동 안내, 사고·보호자 통지를 하나의 사건으로 연결합니다.
- 도감은 지원 차량의 전체 경고등·표시등·계기판 오류 문구를 대상으로 합니다. 대표 경고등 세 개만 지원하는 계획은 폐기됐습니다.
- 사용자가 모양을 직접 찾거나 정차 후 사진으로 후보를 확인하도록 합니다. 공식 해설과 대처, 필요한 경우 현대 서비스센터 찾기로 이어집니다.
- 소리·영상·차량 상태는 실제 제공 및 권한이 확인된 채널만 기록합니다. 진동 분석과 내부·외부 마이크, 블랙박스 연동은 실제 대상 지원을 확인해야 합니다.
- 긴급 안내는 음성과 Pleos 화면의 그림·설명 애니메이션이 같은 단계를 보여 줘야 합니다. 센서가 없거나 오래되면 직접 상황 선택을 제공합니다.
- 사고 때 등록 보호자에게 위치와 받은 사실을 알리고, 차량 전원 중단에 대비해 사전에 준비한 휴대폰이 가능한 기능을 이어받도록 설계합니다.

### 문서와 참가 정보

- **개인 참가**입니다. 개인 체크와 인원 1명, 앱명만 반영했습니다.
- 성명, 연락처, 소속, 참가 부문, 날짜, 동의 표시, 서명은 사용자가 직접 작성합니다. 임의로 채우지 않습니다.
- 제목 계층은 현대차 공모전 양식을 따릅니다. 01~04 영역과 앱 소개의 1~8번 순서를 유지합니다.
- 기획 부분의 문서 디자인은 세션 `01a1b3d8-8797-7880-83dd-b2f3b81029e8`의 사용자 수정본을 참고합니다. 페이퍼로지 글꼴, 표·여백·캡션 스타일을 적용했습니다.
- 위 참고 문서의 ■·●·○ 제목 기호나 PSST 목차는 가져오지 않습니다. 사용자가 공모전 양식의 제목 계층을 다시 지정했습니다.
- **03 동의서와 04 서명란은 공모전 원본의 디자인 그대로 유지합니다.** 원래 글꼴, 색, 들여쓰기, 체크박스와 표 테두리에 새 문서 스타일을 덮지 않습니다.
- 2~6번만 각각 3,000자로 확장했습니다. 한 줄 소개, 참고자료, 숏폼은 변경 대상에서 제외했습니다.
- 설명은 쉬운 한국어와 존댓말을 사용합니다. 실제 구현·확인한 사실과 앞으로 할 일을 분리하고, 반복 문구로 분량을 채우지 않습니다.

## 5. 공식 양식의 항목과 글자 수

공식 양식은 내부 제어 태그의 오래된 이름과 보이는 제목이 서로 다릅니다. **보이는 항목 번호를 기준으로 매칭**해야 합니다.

| 보이는 항목 | 제어 태그 | 최신 처리 |
| --- | --- | --- |
| 1. 앱 한 줄 소개 | `app_summary` | 기존 한 문장 88자 유지 |
| 2. 기획 배경 | `planning_background` | 3,000자 |
| 3. 앱 주요 기능 및 차량 특화 요소 | `vehicle_scenario` | 3,000자 |
| 4. 주요 사용 시나리오 | `key_features` | 3,000자 |
| 5. 개발 계획 | `pleos_plan` | 3,000자 |
| 6. 기대효과 및 발전 가능성 | `reference_files` | 3,000자 |
| 7. 참고자료 | `reference_link` | 기존 자료 안내와 이미지 유지 |
| 8. 숏폼 | `shortform_link` | 기존 미제출 표시 유지 |

3,000자는 **Word의 `ContentControl.Range.ComputeStatistics(5)`**, 즉 공백 포함 문자 수로 확인했습니다. 각 항목은 12개 문단이며 일반 문자·공백 2,978개와 수동 줄바꿈 22개를 합해 3,000자입니다. 항목 제목과 양식 안내문은 작성란 밖이므로 세지 않습니다. 텍스트 파일의 맨 끝 저장용 개행을 제외하면 원고 문자열 길이도 3,000입니다.

공식 공모전이 3,000자를 요구한 것은 아닙니다. 공식 양식에는 소개 자료 분량 제한이 없으며, 이번 길이는 사용자가 지정했습니다. 양식의 ‘4줄 정도’ 안내는 최대 글자 수가 아닙니다. 제출 규정의 근거는 [공식 제출 안내](https://appdevchallenge.auto-hmg.io/guide/submission)와 [원본 DOCX](https://appdevchallenge.auto-hmg.io/downloads/contest-application-consent.docx)입니다. 향후 제출 시에는 그 시점의 공지와 양식을 다시 확인합니다.

## 6. 앱 화면과 이미지 기준

### 승인된 시각 방향

차량 이미지는 공식 자료를 확인한 **디 올 뉴 아반떼** 기준입니다. 테슬라나 정체가 불분명한 일반 차량 이미지로 바꾸지 않습니다. 홈은 차량 모습을 중심에 두고 앞부분·타이어·실내·뒤쪽을 직접 선택하도록 구성했습니다. 부위를 모르는 사람은 증상에서 시작할 수 있습니다.

사용자는 이모지가 아니라 **아이콘**을 요청했습니다. 경고등은 모양, 기록은 파형·시간표, 긴급 상황은 별도 위험 화면·페달 그림, 보호자 확인은 지도와 전달 상태로 구분합니다. 긴급 화면에 평상시 탐색 메뉴를 그대로 남겨 두지 않습니다.

| `acceptance-scenarios.json` | v2.0.0, 검증 시나리오 56개 | 구현 뒤 실행할 기준 |
| SDK 자료 | 공개 문서, 패키지 선언과 일부 정적 분석 | 대상 차량에서의 실제 수신 증거와 구별 |

의도한 처리 흐름은 다음과 같습니다.

```text
허용된 Pleos·AAOS 입력 + 사용자 상황 선택
  → 출처·시각·품질 확인
  → 차량 안 판정 및 사건 기록
  → 같은 단계의 화면·음성 안내
  → 사건 요약 우선 전송, 확보된 원본 자료 추가 전송
  → 서버의 보호자 확인·발송 정책
  → 알림톡 요청, 실패·전달 미확인 때 문자 전환

사전 연결된 안드로이드 휴대폰
  → 마지막 사건·단계·자료를 보관
  → 차량 중단 시 가능한 안내·전송을 이어받음
```

다음은 아직 완료되지 않았습니다.

1. Pleos 앱, 안드로이드 보조 앱, 실제 API 서버와 데이터베이스 운영 코드.
2. 대상 Pleos 차량 전체 경고등·표시등·문구의 검토 완료 데이터베이스.
3. 실제 차량별 권한, 센서 지원·주기·단위·수신 기록과 자동 판정 검증.
4. 대상 차량의 공식 비상 절차와 장치 배치를 대조한 안내·음성·애니메이션 묶음.
5. 내부·외부 마이크, 카메라, 블랙박스의 실제 연동 결과.
6. 발송사 계약·승인 템플릿·수신 결과 조회·문자 전환을 실행한 기록.
7. 전원 중단·휴대폰 인계·운전 중 표시 제한·가청성을 실제 환경에서 시험한 기록.

## 8. 기술적으로 유지해야 할 조건

- 신호가 없다는 사실을 값 0이나 브레이크 미입력으로 바꾸지 않습니다. 브레이크는 `true`, `false`, 확인 불가를 나누며 불리언 값으로 발의 위치·힘을 확정하지 않습니다.
- 신호마다 출처·측정 시각·품질을 관리합니다. 3,000ms 이상 오래된 자료는 수동 선택 전환 기준에 포함합니다. 재조회한 캐시로 측정 시각을 새로 만들지 않습니다.
- 원시 CAN/VHAL에 일반 앱이 직접 접근하는 구조나 확인되지 않은 모터 RPM·고장 코드 API를 만들어 적지 않습니다.
- 진동·충격 임계값은 실험값입니다. `production_motion_model_approved=false`를 운영 검증 없이 바꾸지 않습니다. 겹친 분석 창을 각각 독립된 충격으로 세지 않습니다.
- 사용자의 당황한 음성은 보조 정보입니다. 음성 한마디나 단일 가속 값으로 급발진 원인·페달 오조작·부상 정도를 확정하지 않습니다.
- 검토된 차량별 안내를 사용하며 긴급 조작 순서를 LLM이 즉석에서 만들지 않습니다. 음성과 그림은 같은 `guide_id`, `version`, `step_id`를 사용합니다.
- 사건 요약은 먼저 보관·전송하고, 보호자 통지는 요청한 10초 확인·즉시 발송·취소 정책을 따릅니다.
- 발송사 접수, 실제 전달, 보호자 열람은 서로 다릅니다. 응답 없음은 의학적 의식 소실 진단이 아닙니다.
- 알림톡 실패·전달 미확인 시 문자 전환 기한은 첫 발송 요청부터 서버가 관리합니다. HTTP 응답이 끊긴 경우도 포함합니다. 일반 알림에 OTP 전용 API를 사용하지 않습니다.
- 휴대폰 백업은 사전에 준비합니다. 차량 전원이 꺼진 뒤 새로운 차량 센서값을 복원하거나 보조 앱이 항상 자동 실행된다고 가정하지 않습니다.
- 1280×720dp는 설계용 앱 영역입니다. 모든 Pleos 차량의 실제 패널 해상도라고 쓰지 않습니다. 시스템 보호 영역, 창 크기 변화, 주행 중 표시·조작 제한을 준수합니다.

## 10. 문서를 수정하는 방법

### 최신 파일을 먼저 보존합니다

현재 Word·PDF와 검증 JSON의 해시를 대조하고, 사용자가 직접 수정한 최신 파일이 있다면 먼저 비교합니다. 기존 `qa/` 기준 사본은 수정 이력으로 보존합니다. 새로운 수정의 기준을 정하지 않은 채 옛 사본에 덮어쓰지 않습니다.

| 스크립트 | 용도 | 주의점 |
| --- | --- | --- |
| `build_documents.py` | 원본 양식과 Markdown으로 두 문서를 구성한 초기 빌더 | 단독 실행하면 최신 페이퍼로지 스타일·3,000자 원고가 되돌아갈 수 있음 |
| `restyle_documents.py` | 참고 세션 디자인 적용과 원본 동의서 스타일 복원 | `qa/paperlogy/baseline/`에서 읽으므로 최신 공식 확장 내용을 그대로 보존하는 편집기가 아님 |
| `expand_official_content.py` | 현재 다섯 원고를 공식 작성란에 반영 | `qa/content3000/baseline/`의8쪽 기준 사본을 사용. 그 뒤 추가된 수동 수정은 별도 대조 필요 |
| `verify_content3000.py` | 최신 확장 결과 대조와 ZIP 갱신 | 최신 Word·PDF 변환과 시각 검수를 대신하지 않음. 경로·예상 쪽수와 기존 기록을 고정해 읽음 |
| `verify_final_documents.py` | 이전 디자인 단계의 검증 | 공식8쪽을 전제로 하므로 현재14쪽 최종 검증으로 사용하지 않음 |
| `build_ui_final.py` | 차량 중심 최신 UI 이미지 생성 | 옛 `build_ui.py`, `build_ui_v2.py` 출력을 최종 UI로 사용하지 않음 |
| `finalize_content_count.py` | 최초 원고의 글자 수를 다듬은 보조 스크립트 | 임의의 새 원고를 자동으로3,000자로 만드는 도구가 아님 |

**현재 원고만 다시 반영할 때의 순서**는 다음과 같습니다. 인계만 받았다는 이유로 재실행할 필요는 없습니다.

1. 현재 파일과 `qa/content3000/baseline/`의 차이를 확인합니다. 추가 수동 수정이 있으면 먼저 반영할 기준 사본을 정합니다.
2. [다섯 원고](submission/official-content-3000/README.md)를 수정하고 글자 수를 확인합니다. 이름이나 인원을 새로 넣지 않습니다.
3. 기준 사본을 확인한 뒤 `expand_official_content.py`로 작성란2~6번만 반영합니다.
4. 최신 DOCX를 Word에서 열어 작성란의 `ComputeStatistics(5)`를 다시 측정하고 **새 결과**를 저장합니다.
5. 같은 최신 DOCX에서 PDF를 내보냅니다. 실패하면 이전 PDF를 최신 변환 결과로 취급하지 않습니다.
6. PDF를 새 검수 폴더로 렌더링하고 모든 페이지를 직접 확인합니다. 원고 문단 누락·글자 잘림·표 분할·제목 고립과 동의서 원본 서식을 대조합니다.
7. `verify_content3000.py`가 읽는 Word 집계 JSON·렌더 경로·쪽수·비교 기준을 이번 실행에 맞춰 확인한 다음 검증과 ZIP 갱신을 진행합니다.
8. 검증 JSON, 제작 기록, 이 인계 문서의 현재 파일 해시와 쪽수를 함께 갱신합니다.

현재 검증 스크립트는 `qa/content3000/word-counts-final.json`과 `render2/`, 공식14쪽을 읽도록 작성돼 있습니다. **스크립트만 실행해도 Word 글자 수를 새로 측정하거나 새 시각 검수를 수행하는 것은 아닙니다.** 소스가 바뀌었다면 이전 JSON·PNG를 그대로 재사용하지 않습니다.

### 사용한 환경과 변환 방법

문서·이미지 관련 Python/Node는 `load_workspace_dependencies`가 반환한 번들 경로를 사용합니다. 현재 확인된 실행 파일은 다음과 같습니다. 앱 업데이트 후에는 다시 조회합니다.

```text
Python
C:/Program Files/WindowsApps/OpenAI.CodexPrimaryRuntime.v26-1104-2876-0_26.1104.2876.0_x64__3k8sg7r9htsxt/dependencies/python/python.exe

Node
C:/Program Files/WindowsApps/OpenAI.CodexPrimaryRuntime.v26-1104-2876-0_26.1104.2876.0_x64__3k8sg7r9htsxt/dependencies/node/bin/node.exe
```

문서 스킬의 `render_docx.py`는 LibreOffice 실행 파일이 없어 실패했습니다. 그 뒤 Microsoft Word의 별도 숨김 COM 인스턴스로 PDF를 내보내고 Poppler `pdftoppm -scale-to 1600 -png`로 검수 이미지를 만들었습니다. 사용자의 기존 Word 창을 재사용하거나 다른 프로세스를 종료하지 않았습니다. COM 시작이 한 차례 실패한 뒤 새 시도에서 정상 변환됐습니다. PowerShell은 오류 시 중단하고, 자신이 만든 Word 인스턴스만 닫아야 합니다.

공식 문서의 Poppler 렌더에서 Symbol/ArialUnicode 대체 글꼴 경고가 있었으나 모든 페이지의 글자와 체크박스를 확인했습니다. 기존 PDF를 읽는 라이브러리는 `pypdf`, `pdfplumber`, 이미지 대조는 Pillow를 사용했습니다. 이 인계 작성에서 Word/PDF를 재렌더링하지는 않았습니다.

## 11. 검증 결과와 그 한계

### 이미 실행한 확인

- Word에서2~6번 모두 공백 포함3,000자를 확인했습니다. 결과는 `output/submission/qa/content3000/word-counts-final.json`에 있습니다.
- 다섯 원고의60개 문단이 모두 최종 PDF에 포함돼 있습니다.
- 공식14쪽 전체를 원본 크기로 확인했습니다. 현재 검수 경로는 `output/submission/qa/content3000/render2/`입니다.
- 별첨40쪽은 앞선 작업에서 전체를 확인하고 바뀐8쪽을 다시 검사했습니다. 마지막 공식 양식 확장에서는 별첨 두 파일이 바이트 그대로 유지됐습니다.
- 공식 문서 패키지에서는 `word/document.xml`만 바뀌었습니다. 동의서·서명 영역의 XML, 글꼴·스타일·이미지는 보존했습니다.
- 동의서·서명은13·14쪽으로 이동했습니다. 페이지 번호가 갱신됐으며 서명 밑줄 일부의 PDF 좌표에 최대0.01512pt의 반올림 차이가 있습니다. 원본 서식 변경으로 기록하지 않습니다.
- ZIP에는 최신 문서4개만 있고 압축 안의 파일 바이트가 실제 파일과 같습니다.
- 인계 작성 시 위 최종 파일들의 해시와 PDF14/40쪽을 다시 확인했습니다. 확인을 위해 산출물이나 ZIP을 다시 생성하지 않았습니다.

### 검증하지 않은 것

실제 앱 빌드, API 서버 실행, 실제 차량 센서, 도감 전체 콘텐츠의 최종 검토, 카카오톡·문자 발송, 블랙박스 캡처, 휴대폰 인계, 운전 중 사용성 및 사고 대응 성능은 완료된 검증이 아닙니다. 이전 정적·합성 검사와 문서 검수를 이러한 실행 증거로 바꾸어 설명하지 않습니다. 공모전에 실제 제출하거나 접수 성공을 확인한 기록도 없습니다.

## 12. 후속 작업의 원칙

사용자가 문서를 더 고쳐 달라고 하면 수정할 부분을 현재 원고·승인 시안과 연결해 바꾸고 재검수합니다. 실제 개발을 요청하면 먼저 대상 환경에서 제공되는 기능을 확인한 뒤 모의 입력과 실제 입력을 구분하는 작은 실행 흐름부터 구현합니다. 지금 인계 요청만으로 개발·배포·제출을 시작하지 않습니다.

외부 이메일·카카오톡·문자 발송은 명시적인 요청 없이 수행하지 않습니다. 비밀키·토큰·연락처·서명을 문서나 로그에 임의로 넣지 않습니다. 다른 에이전트의 프로세스·세션·Claude 앱을 종료하거나 재시작하지 않으며, Orca나 관련 훅도 요청 없이 재설치하지 않습니다.

다음 작업을 마친 뒤에는 이 문서의 현재 상태, 산출물 경로와 해시, 남은 작업을 갱신합니다. 상세 사실의 기준은 각 분야의 기존 보고서와 검증 기록이며, 새 인계 파일을 여러 개 만들어 서로 다른 결론을 유지하지 않습니다.
